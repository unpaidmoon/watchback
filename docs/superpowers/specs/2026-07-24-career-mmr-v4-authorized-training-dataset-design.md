# 生涯 MMR v4：授权多玩家隔离训练数据集设计

## 1. 背景

当前生涯 MMR v4 已完成技术评估与正式设计：

- v3 已具备版本化 artifact、事务激活、回滚和运行时验证框架；
- v4 计划采用成熟基础评分算法挑战者、TrueSkill 2 风格表现证据和对称职责基线；
- 现有训练数据只有少量独立账号，无法可靠证明跨玩家泛化；
- 已有约 20 位明确授权参与训练的玩家，每位提供可由同一组登录凭据访问的
  `customerToken`；
- 每位参与者固定采集 S15、S20、S21、S22、S23。

本设计只覆盖开发训练用途的数据采集、隔离导入和 v4 训练前门禁。它不在正式
Watchback UI 中新增任意玩家查询能力，也不改变“正式产品仅同步当前浏览器登录
账号”的产品边界。

## 2. 目标

1. 从当前 `codex/code-review` HEAD 创建隔离开发工作树。
2. 使用一组有效且匹配的 `token + roleId`，批量采集 20 位授权参与者的五个赛季。
3. 将每位参与者保存为独立、可幂等更新的 SQLite 训练源。
4. 支持断点续传、部分详情补抓、429 退避和凭据失效早停。
5. 让现有 `discover_training_sources` 与多账号训练投影器直接消费隔离数据。
6. 在运行 v4 实验前执行匿名数据覆盖门禁。
7. 单轮 v4 release 实验硬上限为 30 分钟；候选失败时保留 v2。
8. 凭据、参与者身份、原始 JSON、SQLite 和训练中间数据不进入 Git。

## 3. 非目标

- 不修改正式登录、账号绑定或同步 UI。
- 不恢复或扩展正式产品中的 `searchBnetAccount` 旧流程。
- 不批量采集未经授权的玩家。
- 不把 `customerToken`、BattleTag 或凭据写入训练报告、日志或检查点。
- 不直接用原始 JSON 绕过现有 SQLite 投影和数据质量逻辑。
- 不保证 v4 一定上线，也不生成强制非零兜底模型。
- 不在本设计阶段修改 v4 模型数学或发布新的 runtime artifact。

## 4. 隔离边界

### 4.1 Git 工作树

工作树从设计获批时的当前 HEAD 创建：

```text
branch: codex/career-mmr-v4-training
path:   D:\Codex\OW_data\owstats-career-mmr-v4-training
```

工作树只保存源码、合成测试、设计、计划和可公开的匿名报告格式。它不得保存真实
凭据、清单、玩家数据、SQLite、浏览器 profile 或模型训练中间产物。

### 4.2 私有训练目录

真实数据位于工作树之外的操作者指定目录。推荐布局：

```text
<private-training-root>/
├─ credentials.json
├─ participants.json
├─ accounts.json
├─ accounts/
│  ├─ <account-id-001>/
│  │  ├─ account.json
│  │  ├─ owstats.sqlite3
│  │  └─ seasons/
│  └─ ...
├─ .training-operations/
│  ├─ checkpoints/
│  └─ staging/
└─ outputs/
```

真实身份可以存在于私有账号 manifest 和原始上游数据中，因为现有导入器需要识别
当前玩家；对外输出始终使用 `dataset-001` 至 `dataset-020`。不得用运行时递归
脱敏改写原始数据。

## 5. 批量清单与凭据

清单为本地 JSON，固定五个赛季：

```json
{
  "schemaVersion": 1,
  "seasons": [15, 20, 21, 22, 23],
  "participants": [
    {
      "datasetId": "dataset-001",
      "customerToken": "<private>"
    }
  ]
}
```

规则：

- `schemaVersion` 首版只接受 `1`；
- `seasons` 必须精确为 S15、S20、S21、S22、S23，顺序规范化；
- `datasetId` 必须唯一并符合 `dataset-NNN`；
- `customerToken` 必须非空，且重复值视为配置错误；
- 未知字段默认拒绝，避免拼写错误被静默忽略；
- 登录凭据与参与者清单分离；
- 登录凭据必须包含有效 `roleId`、`token`，可选 `dts` 与 `server`；
- CLI 只接收凭据文件路径，不接受把登录 token 直接写入命令行参数。

清单和凭据的清理由操作者负责。程序不得复制登录凭据到参与者账号目录、注册表、
检查点或训练报告。

## 6. 采集与导入数据流

每次批处理按以下顺序执行：

1. 校验工作树外的私有根目录、凭据文件和参与者清单。
2. 校验 20 个匿名参与者编号和固定赛季集合。
3. 使用资料卡接口验证每个 `customerToken` 可访问，并取得导入所需身份。
4. 为每位参与者创建独立账号目录、manifest 与 SQLite。
5. 依次处理 100 个“参与者 × 赛季”工作单元。
6. 抓取对局列表、普通详情与角斗详情，保留上游自然出现的字段和错误。
7. 先写 staging 快照；结构校验成功后原子发布赛季快照。
8. 使用现有导入路径写入该参与者 SQLite。
9. 校验赛季、比赛、详情和训练投影的匿名计数。
10. 原子提交该工作单元的检查点。

显式提供 `customerToken` 时，采集器不得调用 BattleTag 搜索去改变目标。资料卡身份
只用于验证、导入和防止目标错配。

## 7. 调度、限速与错误处理

### 7.1 调度

- 同一时间只运行一个“参与者 × 赛季”工作单元；
- 单元内部详情并发固定为 `2`；
- 全局账号请求窗口保持每秒最多 `5` 次；
- 所有参与者共享同一全局限速器；
- 不允许通过多进程绕过限速；
- 默认包含普通与角斗模式。

### 7.2 重试

- 429、超时和临时网络失败使用现有退避策略；
- 原始上游错误进入私有赛季数据和 SQLite 的既有错误面；
- 日志只输出阶段、匿名计数、耗时和文件大小；
- 持续 429 时暂停批次，不提高请求速率；
- 登录 token 失效或 `roleId` 不匹配时立即停止整个批次；
- 身份校验失败时停止对应参与者，并使全量数据集门禁失败。

### 7.3 状态机

```text
pending
→ fetching_list
→ fetching_details
→ importing
→ validating
→ completed
         ↘ partial
         ↘ failed
```

- `completed`：默认跳过，只有显式 `--refresh` 才重新处理；
- `partial`：只补抓缺失详情，并重新执行幂等导入；
- `failed`：从最近已提交的安全阶段恢复；
- staging 中断：不发布临时快照，下次重新处理当前阶段；
- 已提交 SQLite 数据永不因后续失败而回滚到空状态。

## 8. 检查点

检查点不得包含凭据、身份、原始路径或 payload。示例：

```json
{
  "schemaVersion": 1,
  "datasetId": "dataset-001",
  "season": 15,
  "state": "completed",
  "entries": 420,
  "details": 417,
  "failedDetails": 3,
  "attempts": 1
}
```

检查点只用于恢复控制，不替代 SQLite 或赛季快照。检查点写入采用同目录临时文件、
刷新和原子替换。

## 9. SQLite 与训练源兼容

每位参与者使用一个独立账号数据库。必须满足：

- schema 与当前 `matches`、`hero_dict`、`match_players`、`match_details` 训练要求兼容；
- schema 变更仍通过现有幂等迁移；
- 同一参与者重复同步同一赛季不产生重复比赛或训练样本；
- 所有查询和导入明确携带 season；
- 两位参与者即使出现在同一真实比赛中，也保留两个当前玩家训练样本；
- 训练投影为它们生成共享比赛分组键，避免账号留出或 bootstrap 泄漏；
- 备份数据库、链接、重解析点和私有根之外的文件不得成为训练源；
- `discover_training_sources` 能从隔离根目录发现全部有效参与者；
- 任一目标数据库失败不能被静默忽略。

## 10. 采集完成门禁

在进入 v4 实验前，生成仅含匿名聚合的覆盖报告。必须检查：

1. 20 个参与者全部通过资料卡身份确认。
2. 计划单元固定为 100，并报告完成、部分成功与失败数量。
3. 每位参与者至少有一个非空有效赛季；空赛季允许存在并单独计数。
4. 所有 SQLite 均通过 schema 校验和只读打开校验。
5. 数据库之间不存在目录或文件身份冲突。
6. 重复导入抽样验证保持幂等。
7. 普通与角斗正式训练投影均有匿名计数。
8. 报告详情覆盖率和失败详情数，不把 partial 宣称为完整。
9. 任一参与者完全不可用时，不得宣称完整数据集成功。

门禁失败时停止，不运行模型实验。

## 11. v4 实验早停协议

采集门禁通过后，按既有 v4 设计执行：

1. 统一投影器生成全量匿名投影，目标 10 秒内完成。
2. 检查账号、赛季、职责、模式和关键特征覆盖。
3. 正式角斗投影为 0 时立即停止。
4. 先运行固定职责模板的快速烟测。
5. 修正分布单边、三个职责模型相同、存在非有限值、越界或方向反转时立即停止。
6. 比较 v2、Glicko-2 和 TrueSkill 基础挑战者；没有候选不劣于 v2 时保留 v2。
7. 使用账号留出和按时间方向的赛季留出，不允许本场结果泄漏。
8. 单轮实验必须使用 release 二进制，硬上限为 30 分钟。
9. 超时、候选为 0 或门禁失败时停止，不进入 1,000/10,000 次 bootstrap。
10. 不降低门槛，不生成强制非零兜底。
11. 只有训练、留出验证和真实产品 SQLite 重放对账均通过，才生成候选 artifact。

提前停止报告必须说明阶段、实际耗时、失败门槛、已验证覆盖、是否值得修复后重试，
以及是否继续保留 v2。

## 12. 测试设计

所有自动化测试只使用合成凭据、匿名身份和合成 payload。

### 12.1 清单与路径

- 正确清单解析；
- schema 版本、固定赛季、重复编号、重复 token、空值和未知字段拒绝；
- 私有根目录边界；
- 符号链接、Windows 重解析点和路径逃逸拒绝；
- 登录凭据不复制到账号目录。

### 12.2 HTTP 与状态机

- 资料卡成功和身份错配；
- 空赛季；
- 429 退避；
- 超时和临时失败；
- 登录凭据失效导致批次早停；
- 部分详情失败；
- 中断恢复；
- `completed` 跳过；
- `partial` 定向补抓；
- `--refresh` 显式更新。

### 12.3 导入与隔离

- 重复执行不增加重复比赛、详情或训练样本；
- 两个参与者不能互写数据库；
- 五赛季查询不混读；
- 训练 schema 兼容；
- `discover_training_sources` 可发现合成隔离数据；
- 多账号训练投影可读取全部合成源。

### 12.4 隐私合同

扫描日志、检查点和匿名报告，拒绝：

```text
token
customerToken
cookie
authorization
credential
BattleTag
真实本地路径
原始 payload
```

该扫描只针对最小化输出面，不修改或遮盖私有原始运行时数据。

## 13. 实施阶段

### 阶段一：隔离批量采集

1. 创建工作树和开发分支。
2. 实现清单解析、安全路径和匿名检查点。
3. 抽取或复用单参与者赛季抓取与导入能力。
4. 实现全局限速、恢复和匿名审计。
5. 完成合成测试与精准回归。
6. 由操作者提供私有目录后运行真实 20 × 5 批次。
7. 生成匿名数据覆盖报告。

阶段一不修改正式 UI，不替换正式模型。

### 阶段二：v4 早停实验

1. 只有阶段一门禁通过才开始。
2. 按既有 v4 设计统一训练与正式重放投影器。
3. 运行快速覆盖与固定模板烟测。
4. 在 30 分钟硬上限内比较基础评分挑战者和表现证据。
5. 失败则保留 v2并交付停止报告。
6. 通过后再设计 artifact 激活、迁移、查询、UI 和发布验证。

## 14. 验证与交付

开发过程中优先运行受影响的精准测试。阶段一代码完成后至少执行：

```powershell
cd apps\owstats-desktop\src-tauri
cargo fmt --check
cargo test --test <affected-target>
```

最终影响覆盖全局时再执行：

```powershell
cargo test --tests
cd ..
npm test
npm run build
```

正式发布 artifact 变更才要求 `npm run tauri build`；单纯开发训练采集器不触发安装包
发布。所有修改后运行 `git diff --check`，并确认 `git status --short` 只有预期文件。

交付报告必须列出：

- 实际执行命令与结果；
- 计划、完成、partial 和失败工作单元；
- 匿名比赛、详情、职责、模式和赛季覆盖；
- 各阶段耗时；
- v4 是否值得继续；
- 未验证项；
- 是否处理真实隐私数据。

采集程序预计会处理真实凭据和授权玩家原始数据，但开发和报告过程不得读取、回显、
复制到 Git 或扩散这些内容。私有数据与临时输出的清理由操作者负责。
