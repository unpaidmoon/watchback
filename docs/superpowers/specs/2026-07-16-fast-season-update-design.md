# OWStatsLocal 快速赛季更新与全量抓取设计

日期：2026-07-16

## 1. 背景

现有赛季同步已经做到详情增量抓取：本地存在有效详情的对局不会重复请求详情。但是，每次同步仍会对普通模式与角斗模式的赛季列表从第一页扫描到空页。赛季数据量增长后，列表请求仍会使日常更新耗时较长。

本设计把赛季同步拆成两个用户可见入口：

- **更新**：默认用于快速获取最近新增对局，优先保证速度。
- **全量抓取**：扫描完整赛季并重新抓取全部详情，用于首次同步、历史补录检查和彻底修复。

用户接受以下边界：如果上游把旧时间的对局延迟补到快速扫描范围之外，“更新”可能暂时无法发现；执行“全量抓取”后必须发现并导入。

## 2. 目标

- 已有有效水位、第一页协议有效且上游无变化时，“更新”只请求每种模式的第一页，详情请求为零。
- 有少量最新对局时，“更新”只扫描覆盖新对局所需的少量页面，只请求新对局或扫描范围内缺失详情。
- 多种模式并行检查当前页，使无变化更新的整体耗时接近一次列表请求。
- “更新”具有明确性能上限，不退化为完整赛季扫描。
- “全量抓取”保留完整扫描和全详情刷新能力。
- 首次同步继续能够获得完整赛季数据。
- 两种模式共用账号校验、限速、重试、脱敏、落库和快照逻辑。
- 不删除或缩小未扫描到的历史数据。

## 3. 非目标

- 不保证“更新”发现上游延迟写入到历史深处的对局。
- 不把快速停止条件描述为完整性证明。
- 不新增定时后台同步、自动轮询或一键同步全部赛季。
- 不新增全局赛季状态。
- 不在快速更新中遍历和修复历史深处所有缺失详情。
- 不恢复 BattleTag 搜索或旧的账号绑定同步流程。

## 4. 用户界面

### 4.1 全量抓取

赛季选择区保留现有赛季下拉框。原主同步按钮改名为“全量抓取”。

- 操作对象是左侧当前选择的赛季。
- 首次同步未在右侧形成赛季数据行时，用户通过这里完成首次抓取。
- 任一同步正在运行时按钮禁用。
- 进度与结果文案必须明确使用“全量抓取”。

### 4.2 更新

右侧“已同步数据”表增加“操作”列。每个已有数据的赛季行，在详情覆盖进度条右侧提供次级按钮“更新”。

- 点击后直接更新该行赛季。
- 不改变左侧当前选择的赛季。
- 按钮视觉紧凑，但交互命中区域不小于 `44px`。
- 赛季行选择区域与“更新”按钮必须是分离的合法交互元素，不得出现按钮嵌套按钮。
- 任一同步正在运行时，所有行内“更新”按钮禁用。
- 当前正在更新的行显示稳定的中文状态，不改变表格列宽。

界面继续遵循根目录 `design.md`：使用现有灰绿表面、黑灰文字、低对比边线、现有圆角和焦点样式，不新增品牌色、阴影体系或卡片层级。

## 5. 同步模式

后端定义显式同步模式，名称可按代码惯例实现，但语义固定为：

- `QuickUpdate`：快速更新。
- `FullFetch`：全量抓取。

Tauri 同步请求携带模式字段。命令入口继续校验当前活动账号、登录凭据与同步目标，然后把模式传入统一同步门面。

同步协调器继续保证同一时间只有一个账号操作或同步写入任务。两种模式不得复制账号、隐私、数据库或快照逻辑。

## 6. 本地快速同步状态

快速更新开始时，按目标赛季和上游模式读取：

- 本地已有 `match_id` 集合。
- 本地已有有效详情的 `match_id` 集合。
- 本地最新有效 `beginTs`，作为该模式的时间水位。

普通模式与角斗模式分别维护水位和停止状态，不得使用一个赛季级水位替代各模式水位。

只有符合当前有效对局协议、具有非空 `matchId` 和有效 `beginTs` 的记录才能参与水位判断。缺失或无效时间不得被转换为零值后参与提前停止。

快速更新不把历史深处已有但缺少详情的对局加入全局修复队列。只有本次实际扫描到的记录可以成为详情请求候选。

## 7. 快速更新分页算法

### 7.1 并发模型

- 每种模式内部必须按页顺序推进，先处理当前页，再决定是否请求下一页。
- 不同模式可以并行请求各自当前页。
- 不得继续使用一次预取五页的批量方式执行快速更新，因为预取会抵消提前停止的收益。
- 全量抓取可继续使用批量并发分页。

### 7.2 单模式停止规则

每种模式从第一页开始。处理一页时：

1. 提取原始条目和符合协议的有效条目。
2. 按 `matchId` 去重。
3. 记录本页新对局、扫描范围内缺失详情和已有完整对局数量。
4. 如果页面为空，立即结束该模式。
5. 如果页面包含本地不存在的 `matchId`，收集这些对局并继续下一页。
6. 如果本页全部有效对局都已在本地存在，并且所有有效 `beginTs` 都不晚于该模式本地时间水位，立即结束该模式。
7. 如果有效条目缺少可用于确认边界的时间、响应结构异常或不能安全判断是否越过水位，不得据此宣称已是最新；继续到性能上限或遇到空页。

首次没有本地水位的赛季不得使用快速停止算法完成首次同步。未形成已同步赛季行时，界面也不提供“更新”入口。

### 7.3 性能上限

`QuickUpdate` 每种模式最多请求 5 页。

该值是快速操作的性能预算，不是“后续页面必然没有新数据”的判断依据。达到上限但没有命中可靠停止边界时：

- 保存本次已发现并成功抓取的数据。
- 同步结果标记为快速扫描范围受限。
- 用户可见提示为“快速更新已达到扫描范围，如需完整校验请使用全量抓取”。
- 不得显示“已是最新”或“完整校验完成”。

`FullFetch` 不使用此快速性能上限，继续扫描到空页。

## 8. 详情抓取

### 8.1 快速更新

详情请求集合仅由本次实际扫描范围中的以下记录组成：

- 本地不存在的新对局。
- 本地已有列表记录，但详情缺失、损坏或与对局身份不一致的记录。

扫描范围之外的历史缺失详情不参与快速更新。详情集合按 `match_id` 去重，并根据对局类型调用普通或角斗详情端点。

### 8.2 全量抓取

全量抓取扫描全部列表页，并对完整去重列表重新请求详情，不复用“已有有效详情则跳过”的快速过滤。

它负责：

- 首次完整同步。
- 发现快速范围之外的延迟补录。
- 重新验证和刷新历史详情。
- 修复历史缺失或损坏详情。

现有限速、详情并发、429 重试和脱敏错误行为保持不变。

## 9. 数据库与快照

两种模式继续使用现有幂等事务与快照边界：

- 对局列表按 `match_id` upsert。
- 只替换本次成功验证的详情。
- 只重建本次成功详情对应的 `match_players` 或 `arena_match_players`。
- 未扫描、未请求或请求失败的历史详情和玩家索引保持不变。
- 成功详情清理对应旧错误，失败详情写入最新脱敏错误。
- 赛季总数和有效详情数从 SQLite 重新查询，不由本次增量数覆盖。
- 数据库提交后，从 SQLite 重建目标赛季完整快照。
- 快照递归脱敏并通过同目录临时文件原子替换。

全量抓取不得因为某场详情失败而删除其旧的有效详情。是否刷新成功以验证后的详情结果为准。

## 10. 进度与结果

快速更新使用以下进度阶段：

1. `正在检查本地水位`
2. `正在快速检查最新对局`
3. `发现 N 场新对局`
4. `正在获取最新对局详情 X / Y`
5. `正在更新本地数据库`
6. `更新完成`

全量抓取使用以下进度阶段：

1. `正在准备全量抓取`
2. `正在扫描完整赛季列表`
3. `正在重新获取全部详情 X / Y`
4. `正在更新本地数据库`
5. `正在重建完整快照`
6. `全量抓取完成`

快速更新结果必须区分：

- 没有变化且可靠命中水位。
- 成功新增对局。
- 部分详情失败，可再次更新。
- 达到快速扫描上限，建议全量抓取。
- 页面异常，未能确认完整边界。

诊断只返回汇总数量、页码、时间范围和阶段耗时，不返回原始 `match_id`、玩家身份或凭据。

## 11. 错误处理

- 列表请求失败时，该模式不得写入未完成的页面结果；整体同步返回安全中文错误。
- 单场详情失败不终止其他详情抓取；新列表记录可以落库，详情保留缺失状态。
- 达到快速扫描上限是可恢复的部分完成状态，不是网络错误。
- 页面没有有效 `matchId` 但又不符合空页协议时，不能作为“已是最新”的依据。
- 数据库更新成功、快照更新失败时，继续使用现有明确的提交边界提示。
- 所有错误、进度、摘要、诊断 JSON 和本地快照继续递归移除或遮盖 token-like 字段。

## 12. 测试策略

### 12.1 快速更新请求数量

- 无变化：每种模式只请求第一页，详情请求为零。
- 新对局位于第一页：只请求新对局详情，并在后续第一张完全已知且越过水位的页面停止。
- 新对局跨多页：扫描覆盖新对局的页面，命中可靠边界后停止。
- 不同模式独立停止，一个模式继续翻页不得迫使其他模式继续。
- 多模式当前页可以并发请求。
- 快速更新不得一次预取五页。

### 12.2 边界与上限

- 本地无水位时不允许通过快速路径完成首次同步。
- 缺少 `beginTs`、无效 `matchId` 和空壳响应不能触发错误的“已是最新”。
- 每模式第 5 页仍未命中边界时停止并返回范围受限提示。
- 达到上限时已发现的新对局仍可安全落库。
- 快速路径不请求扫描范围之外的历史缺失详情。

### 12.3 全量抓取

- 每种模式扫描到空页。
- 对完整去重列表重新请求全部详情。
- 能发现快速扫描范围之外的延迟补录。
- 能修复历史缺失或损坏详情。
- 当前赛季继续保持无显式 `season` 参数优先、显式赛季回退的协议。

### 12.4 UI

- 左侧按钮显示“全量抓取”并作用于当前选择赛季。
- 已同步赛季行显示“更新”。
- 点击行内“更新”不改变左侧选择。
- 赛季选择交互与更新按钮不存在嵌套按钮。
- 任一同步期间所有相关按钮禁用。
- 行内状态不改变表格列宽，窄屏布局仍可操作。
- 所有按钮命中区域与键盘焦点符合 `design.md`。

### 12.5 数据与隐私

- 重复更新保持对局、详情、索引和错误记录幂等。
- 未扫描历史数据不被删除或缩小。
- 全量抓取单场失败不覆盖旧的有效详情。
- 完整快照仍包含旧数据与新数据，并限定目标赛季。
- 请求日志、进度、错误、诊断、SQLite raw JSON 和快照不包含 token-like 敏感数据。

## 13. 性能验收

使用记录请求次数的本地合成服务器验证，不读取真实凭据或真实玩家数据。

必须报告：

- 每个模式的列表请求数。
- 详情请求数。
- 列表、详情和持久化阶段耗时。
- 是否命中本地水位。
- 是否达到快速扫描上限。

硬性验收：

1. 已完整同步且上游无变化时，`QuickUpdate` 每种模式恰好一个列表请求，详情请求为零。
2. `QuickUpdate` 不得扫描到空页后才结束，除非第一页本身为空或页面数据不能安全使用水位。
3. `QuickUpdate` 每种模式不得超过 5 页。
4. `FullFetch` 的请求范围继续覆盖完整赛季并重新请求全部详情。
5. 后端测试、前端测试、构建和 `git diff --check` 通过。

## 14. 验收标准

1. 左侧赛季选择区提供“全量抓取”。
2. 每个已有数据的赛季行在进度条右侧提供“更新”。
3. 行内“更新”直接作用于该行赛季，不改变左侧选择。
4. 快速更新使用分模式本地水位和已知页动态停止。
5. 已有有效水位、第一页协议有效且上游无变化时，每种模式只请求第一页。
6. 快速更新只抓本次扫描范围内的新对局和缺失详情。
7. 快速更新具有每模式 5 页的明确性能上限，并诚实报告范围受限状态。
8. 全量抓取扫描完整赛季并重新获取全部详情。
9. 首次同步由全量抓取完成。
10. 未扫描历史数据、有效详情、玩家索引和赛季统计不被缩小。
11. 两种模式保持账号隔离、赛季隔离、限速、重试、递归脱敏和完整快照要求。
12. 自动化测试用实际请求计数证明快速路径没有退化为全量扫描。
