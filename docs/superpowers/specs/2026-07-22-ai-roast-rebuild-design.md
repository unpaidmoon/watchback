# AI 锐评叙事重构设计

> 状态：设计已确认，等待用户审阅书面规格。
>
> 本文取代 `2026-07-20-ai-match-roast-design.md` 以及本文早期版本中关于锐评素材、模型职责、输出结构、提示词、内容校验和成功态展示的设计。API Key、手动触发、应用级并发锁、账号与对局绑定、凭据存储及既有错误分类继续沿用，除非本文明确调整。

## 1. 背景与问题

当前在途实现已经让 DeepSeek 看到双方完整计分板、职责汇总、个人赛季基准和轻量游戏知识，但最终结果仍然机械。根因不是模型缺少一句“请深入分析”，而是整个生成契约强制模型完成五份作业：本场判词、胜负手、你这局、队友与对位、终审锐评。

该结构同时存在于 Rust 报告 schema、提示词、校验器、TypeScript 类型和 React 成功态中。模型即使识别出真正重点，也必须继续填满其他栏目，最终表现为：

- 默认逐项比较双方同职责数据，最大差值自然变成“胜负手”。
- 同一个结论在多个区块换一种说法重复出现。
- 每个栏目都需要标题和正文，语言像报告模板而不像朋友聊天。
- 为了凑满队友、对位和收尾，次要数据抢走核心故事的篇幅。
- 语气虽然安全，却缺少用户能感受到的立场、理解和节目效果。

本次重构不是给五区块换一套更毒的措辞，而是改变模型的任务：先判断这场比赛究竟在讲什么，再围绕唯一主线写出一篇连续、口语化、有证据的损友复盘。

## 2. 产品目标

用户最终只看到：

```text
一个有趣的主标题

一段连续正文
```

正文长度与当前五区块报告的总量相近，目标约三百五十至五百个汉字。它应当像一位真正懂《守望先锋》的损友发来的一段语音转文字，而不是数据分析师填写的模板。

成功的锐评需要做到：

- 找出最能解释胜负的一个核心矛盾，最多带两个真正相关的辅助因素。
- 理解用户在这场故事中的位置，而不是只看同职责数据差。
- 胜利时优先发掘用户真实亮点，同时明确表扬真正带飞的队友。
- 失败时先说出用户为什么坐牢，再依据证据点出一至两名主要责任人。
- 用户自己是关键问题时诚实指出，但像朋友拆台，不像系统宣判。
- 识别阵容中的关键任务及第一责任人，而不局限于同职责对位。
- 用本局独有的数据反差制造包袱，允许直接、口语化的游戏圈表达。
- 所有事实、比较和责任判断仍可追溯到输入或明确标注的游戏情境推断。

## 3. 核心设计原则

### 3.1 后端准备事实，模型形成理解，后端复核结论

后端负责确定性工作：

- 查询和整理比赛数据。
- 映射稳定的英雄、职责、地图和模式中文名称。
- 计算队内与全场排名、职责汇总、比例、差值、参与率和个人赛季基准。
- 提供与本场阵容有关的英雄类型、特殊英雄解释、地图环境和关键任务知识。
- 建立可引用的证据目录。
- 校验模型有没有写错数字、认错主体、夸大比较或越过推断边界。

模型负责综合判断：

- 识别比赛形状和核心故事。
- 评估不同候选解释，主动寻找反证。
- 判断关键任务、主要承担者和完成结果。
- 确定用户定位、关键人物及责任或功劳顺序。
- 选择与主线有关的证据，舍弃显眼但无关的统计。
- 生成主标题和连续损友锐评。

后端不得恢复“最大职责差就是胜负手”“死亡最多就是主锅”等自动结论规则。职责汇总只是候选证据，不是默认答案。

### 3.2 后台谨慎取证，前台直接说人话

后台使用 `direct_fact`、`statistical_interpretation` 和 `game_context_inference` 区分证据强度。用户可见正文不需要反复出现“可能、一定程度、从数据推断”等分析腔。

证据足够时，正文可以写：

> 这个士兵：76到底在忙什么？法老之鹰在天上都快办年卡了，队里最该把她按下来的就是他，结果对空任务交了张白卷——这把头锅先给他戴好，没什么冤的。

后台仍必须把“对空失职”标为游戏情境推断，并同时引用阵容任务知识、敌方法老之鹰的影响与存活表现，以及我方主要对空职责人的相关战斗数据。

### 3.3 只讲一个核心故事

每场先回答：“如果只能告诉朋友一件事，这局最值得说什么？”该答案成为唯一 `matchThesis`。正文可以包含用户、关键队友和辅助因素，但它们必须服务于同一条主线。

如果删除某项数据不影响核心故事，该数据默认不进入正文。不得为了覆盖所有职责、所有队友或所有输入字段而凑内容。

### 3.4 取悦用户不等于替用户编免责理由

- 胜局采用庆功视角：先寻找用户真实亮点，再表扬真正的大爹。
- 用户被抬赢时可以善意拆台，但不得虚构贡献。
- 败局先承接用户的挫败感，再判断主要责任。
- 有充分证据时可以明确说队友“头锅”“战犯表现”或“把队友当付费陪玩”。
- 用户自己是主要责任人时仍需直说，不能强行把锅移给队友。
- 数据不支持唯一责任人时允许明确写“没有唯一战犯”，但仍要指出最影响结果的环节。

### 3.5 不把最终计分板伪装成录像

当前数据只包含每名玩家的一名英雄记录和整场汇总计分板，没有英雄切换时间线、伤害目标、死亡来源、技能事件或团战时间线。

因此模型可以评价“士兵：76没有完成主要对空任务”，也可以用反问和夸张形成口语化包袱；但后台判断不得建立在“他整局从未攻击法老之鹰”“拒绝换英雄”“某次没有交技能”等无法证明的具体过程上。

## 4. 统一输入模型

普通对局和角斗继续共用统一快照。角斗只追加可靠的回合结果和最终资金，不建立独立缩水流程。

```json
{
  "schemaVersion": 3,
  "matchKind": "standard",
  "match": {},
  "currentPlayer": "我方安娜",
  "scoreboard": {
    "team": [],
    "opponent": []
  },
  "roleMatchups": [],
  "currentPlayerBaseline": {},
  "streak": {},
  "gameKnowledge": {},
  "taskKnowledge": {},
  "arena": null
}
```

### 4.1 比赛与完整计分板

保留胜负、模式、地图、比分、对局时长、双方每名玩家的英雄、职责、战斗数据和可靠派生指标。缺失字段使用 `null` 或省略，不用零值伪装缺失。

派生指标包含适用时的队内与全场排名、击杀参与率、伤害与治疗占比、死亡占比、每次阵亡产出和职责汇总。综合排名只能作为弱参考，不能自动选择主锅或大爹。

### 4.2 当前玩家赛季基准与连续状态

当前玩家同职责赛季基准用于判断本局是否偏离个人通常表现，不取代本场横向比较。连续胜负状态只作为可选娱乐素材，不能压过本局核心故事。

### 4.3 角斗扩展

角斗使用最后一个结构完整、比分可信的有效回合作为完整计分板来源，并追加每回合胜负、回合结束比分和每名玩家最终资金。

模型可以讨论让三追四、决胜回合和最终资金与表现的反差；不能仅凭最终资金断言某个回合或整场胜负原因。

## 5. 游戏知识与关键任务归属

### 5.1 从英雄画像扩展到任务知识

既有轻量知识库继续提供英雄类型、单英雄统计解释和特殊地图环境。本次新增可审查的 `taskKnowledge`，帮助模型判断阵容中谁最应该处理当前关键问题。

任务知识不是固定克制矩阵，也不直接生成主锅。它描述：

- 某类威胁通常需要什么能力处理。
- 本场阵容中哪些英雄是主要承担者，哪些只是辅助承担者。
- 判断任务是否完成时应结合哪些统计结果。
- 哪些结论因缺少事件数据只能作为职责推断。

首版覆盖真正会改变赛后解释的高价值任务：

- 对空与远程威胁处理。
- 前排承压、空间与低收益阵亡。
- 持续输出到击杀或最后一击的转化。
- 后排保护与关键支援生存环境。
- 主要治疗、功能支援和资源转化。
- 目标争夺与战斗参与之间的机会成本。
- 高资源占用与低产出的反差。

### 5.2 第一责任人优先

当多名英雄都能处理同一威胁时，模型优先判断最主要的任务承担者。辅助承担者只有在主责不明确、主责已完成而整体仍失败，或多人的数据共同支持责任分摊时才进入正文。

例如我方同时存在士兵：76、D.Va 和安娜，敌方法老之鹰死亡很低且持续形成高影响时，模型首先检查士兵：76这个最直接的对空职责人，而不是把责任平均分配给所有能碰到空中目标的英雄。

### 5.3 任务判断不是单字段规则

“敌方法老之鹰死亡低”本身不足以自动判定士兵：76失职。模型还需结合：

- 法老之鹰的击杀、最后一击、参与率、伤害和存活表现。
- 士兵：76的伤害、击杀转化、最后一击、参与率和死亡。
- 我方是否存在更直接或同等重要的处理者。
- 队伍是否因后排生存、前排崩溃等更主要问题根本没有形成处理窗口。

最终可以明确下判断，但判断必须来自多维证据而不是单个阈值。

## 6. 模型分析流程

单次 DeepSeek 请求继续使用思考模式。提示词要求模型在写作前完成以下任务：

1. 判断比赛形状：碾压、接近局、单点崩盘、资源转化失败、关键任务无人完成、某人强行抬队，或数据领先却没有转化为胜势。
2. 提出候选解释，并检查是否存在更有解释力的反证。
3. 识别最重要的威胁或任务及其第一责任人。
4. 形成唯一核心故事和最多两个辅助因素。
5. 判断当前玩家在故事中的角色。
6. 按胜负选择情绪立场和功劳或责任顺序。
7. 选择本局独有的数据反差作为笑点来源。
8. 最后生成主标题和连续正文。

提示词必须包含三项自检：

- 如果这段话换到多数其他对局仍成立，说明过于模板化，重写。
- 如果结论只是朗读双方职责差值，继续检查转化、资源、存活、关键威胁和任务归属。
- 如果主标题不能准确概括正文唯一主线，重写标题。

## 7. 模型输出与用户可见格式

### 7.1 提供方响应

模型返回一个 JSON 对象，包含后台分析计划和最终文案：

```json
{
  "analysis": {
    "matchThesis": {
      "judgment": "我方有输出但没有处理最关键的空中威胁",
      "claimType": "game_context_inference",
      "evidenceRefs": ["..."]
    },
    "currentPlayer": {
      "judgment": "有稳定贡献但击杀转化不足",
      "claimType": "statistical_interpretation",
      "evidenceRefs": ["..."]
    },
    "keyActors": [
      {
        "subject": "我方士兵：76",
        "impact": "negative",
        "judgment": "主要对空任务没有形成结果",
        "claimType": "game_context_inference",
        "evidenceRefs": ["..."]
      }
    ],
    "supportingFactors": []
  },
  "title": "输出刷了一整局信用卡，结账时发现没带钱包",
  "commentary": "……"
}
```

后台分析计划不是另一份用户报告。它只用于约束模型先做判断、支持本地校验和后续质量诊断。

### 7.2 用户可见输出

前端只展示：

```text
title

commentary
```

- 标题应有趣且准确概括唯一主线，不使用可换到任意比赛的万能封号。
- 正文为一篇连续叙事，可包含自然段，但不出现栏目标题、项目符号或编号。
- 正文目标三百五十至五百个汉字；数据不足时允许缩短。
- 不规定句数、段数或人物数量，不要求每项输入都被提及。

## 8. 文风：懂游戏的口语化损友

### 8.1 允许的锐度

允许使用“坐牢、头锅、战犯、付费陪玩、任务交白卷、在天上办年卡、把团战打成公益项目”等游戏圈表达。允许反问、夸张和一本正经地描述荒谬反差。

嘲讽对象只能是本局行为、数据结果、任务完成情况和比赛反差。禁止攻击人格、智力、身份、现实生活或受保护特征，也不得推断故意送、摆烂、拒绝交流或主观意图。

### 8.2 胜负语气

胜局：

- 庆功优先，不把胜利写成冷冰冰的审计报告。
- 尽量找到用户真实亮点。
- 有明确带飞者时必须夸真正的大爹。
- 用户被抬赢时善意拆台，不能硬舔或虚构贡献。

败局：

- 开头尽快说出用户为什么觉得坐牢。
- 依据证据优先追究一至两名主要责任人。
- 用户自己有明显问题时诚实指出。
- 不用“大家都有问题”或“已经尽力”完成端水任务。

### 8.3 笑点来源

优先使用本局独有反差：高伤低转化、高治疗仍高阵亡、高资源低产出、关键任务无人完成、职责数据领先却输、用户普通但完成脏活、用户被大爹抬赢、角斗走势与最终资金反差。

避免公关式套话、万能封号、连续堆网络梗和同一篇正文混用多套比喻体系。笑点必须服务于结论，不能替代结论。

## 9. 模型调用

首版继续使用应用内部配置的 `deepseek-v4-flash`，单次主请求完成综合判断和写作，不拆成分析与改写两次计费调用。保持思考模式、较高推理强度、JSON 输出和非零温度；具体参数通过提示词版本统一管理。

一次用户操作最多包含一次主生成和一次有限修正。第二次仍失败则返回既有可恢复错误，不保存部分结果。

## 10. 证据与校验

### 10.1 硬校验

本地校验：

- JSON schema、主标题、正文和后台分析计划完整。
- 所有主体与 `evidenceRefs` 都存在于本次请求的匿名快照或知识上下文。
- 正文中的数字、比例、最高、最低、领先和落后能够由引用证据支持。
- 正文点名的人物、功劳和责任判断能对应到后台分析项。
- `game_context_inference` 同时引用统计证据与任务或游戏知识。
- `matchThesis` 至少结合两个相关维度，不能只引用一项职责差值。
- 辅助因素最多两个，且不与核心故事重复表达同一结论。
- 失败时主要负面责任人最多两名；数据不足时不强行找锅。
- 不出现未提供的玩家、英雄、地图、身份信息、路径或凭据。
- 不出现人格攻击、身份攻击、仇恨表达或无法证明的主观意图。
- 标题和正文符合长度硬上限。

### 10.2 不做机械硬校验的内容

本地不通过关键词数量计算“是否有趣”，不要求固定句数，不要求每场必须出现某类人物，也不恢复大范围普通词黑名单。

标题是否真正有梗、正文是否像朋友、主线是否是最佳解释，需要合成场景与人工盲评共同验收。

### 10.3 有限修正

首次校验失败后，只向模型返回匿名位置、错误类别和修正要求。修正消息不得包含真实身份、路径、凭据、原始响应正文或完整请求 payload。

修正优先保持已通过验证的核心故事，只改正无证据判断、错误引用、结构或长度。核心故事本身缺乏证据时才要求重新选择主线。

## 11. 前端展示

成功态使用一个连续表面：

- 一个有趣的主标题，作为唯一明确加粗层级。
- 标题下方是一篇连续正文。
- 删除五区块栏目、重复的小标题和区块分隔线。
- 允许正文自然分段，但不渲染为多张卡片。
- 保留“重新生成”。
- 重新生成失败时继续展示旧结果和行内错误，不先清空已有内容。

视觉继续遵循根目录 `design.md`：依靠字重、字号、留白和单一连续表面建立层级，不引入新的品牌色、字体、圆角、阴影或卡片语言。

## 12. 存储与兼容

新结果保存：

- 主标题。
- 连续正文。
- 后台分析计划 JSON。
- 报告 schema 版本。
- 输入 schema 版本。
- 知识库与任务知识版本。
- 提示词版本、模型和生成时间。

SQLite 迁移必须前向兼容且幂等，不重写或删除历史锐评。旧标题加正文记录继续原样展示。当前五区块结构记录继续可读并按旧样式展示；用户主动重新生成成功后，原子替换为新版标题加正文。

知识库或提示词升级不自动使已有结果失效。重新生成失败时保留旧记录。

## 13. 测试与验收

### 13.1 输入与知识测试

- 普通和角斗都包含双方完整计分板，而不是预选三至四条事实。
- 字段缺失时不伪造零值。
- 职责汇总、派生指标和当前玩家基准计算正确。
- 不包含玩家名、BattleTag、账号 ID、对局 ID、GUID、路径或凭据。
- 每场只发送本局涉及的英雄、地图和任务知识。
- 关键任务知识能够区分主要承担者和辅助承担者。
- 不确定任务允许留空，不阻塞生成。

### 13.2 合成理解场景

使用纯合成数据覆盖：

- 我方士兵：76是主要对空职责人，敌方法老之鹰低死亡且高影响；模型明确判断主要对空任务失败。
- 同场存在 D.Va、安娜等辅助处理者时，优先追究主要承担者，不平均分锅。
- 我方后排持续高死亡使输出缺少发挥窗口时，不把所有责任简单归给输出。
- 高伤害低击杀转化成为核心故事，而不是只写职责伤害差。
- 支援治疗领先但队伍高阵亡，需要解释资源转化而不是宣布支援完胜。
- 坦克高承伤分别对应有效推进和低收益承伤两种结论。
- 胜局用户有真实亮点且队友明显带飞，同时夸用户与大爹。
- 胜局用户明显被抬，使用善意拆台而不虚构贡献。
- 败局一至两名队友有充分责任证据。
- 用户自己是关键责任人，报告不强行甩锅。
- 接近局没有可靠唯一战犯，但仍选出最有解释力的环节。
- 角斗让三追四和最终资金反差不产生未经证明的因果。

### 13.3 输出与 UI 测试

- 新结果的用户 DTO 只提供主标题和正文作为成功态内容。
- React 不渲染五区块标题和分隔结构。
- 旧记录和五区块在途记录仍可读取。
- 重新生成成功原子替换，失败保留旧内容。
- 主标题是成功态唯一明确加粗层级，正文保持连续阅读。

### 13.4 人工质量验收

对多场合成输出进行盲评，维度包括：

- 准确性。
- 核心主线清晰度。
- 对游戏任务的理解深度。
- 是否理解用户处境。
- 幽默度和口语感。
- 模板重复感。
- 功劳与责任公平性。

每份报告还需回答：

- 换到另一场比赛是否仍然成立。
- 是否只是朗读职责差值。
- 标题是否准确概括正文。
- 删除某个辅助数据后，主线是否仍然一致。

## 14. 非目标

本次不包含：

- 运行时联网搜索游戏知识。
- 完整固定英雄克制矩阵。
- 基于录像或事件时间线的团战复盘。
- 英雄切换、技能使用、目标伤害和死亡来源推断。
- 逐回合角斗详细复盘、装备、异能或构筑分析。
- 多种用户可选文风。
- 长篇专业教练报告。
- 自动生成或分享图片。
- 多轮追问式锐评。

## 15. 成功标准

重构成功需要同时满足：

- 模型使用完整对局和游戏任务知识形成唯一核心故事，而不是默认机械比较同职责数据。
- 能识别阵容中的关键任务、第一责任人和结果反差，同时遵守最终计分板的证据边界。
- 胜利时尽量夸到用户真实亮点并表扬真正的大爹；失败时先理解用户，再公平而直接地找出主要责任。
- 用户只看到一个有趣的主标题和一篇连续正文，不再看到五区块模板。
- 文案口语化、有梗、敢下判断，但不靠虚构事实或人格攻击制造刺激。
- 用户看完会觉得：“它真的知道这局最离谱的地方是什么，也知道我在这局里到底经历了什么。”
