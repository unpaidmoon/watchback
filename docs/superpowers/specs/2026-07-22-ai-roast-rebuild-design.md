# AI 锐评重构设计

> 状态：已确认，等待实施计划。
>
> 本文取代 `2026-07-20-ai-match-roast-design.md` 中关于锐评素材、模型输入、模型职责、输出结构、提示词、内容校验和成功态展示的设计。API Key、手动触发、应用级并发锁、账号与对局绑定、凭据存储及既有错误分类继续沿用，除非本文明确调整。

## 1. 背景与问题

当前实现先在 Rust 中替模型选出三至四条事实，并预先指定至多一个“大爹、短板、主锅或当前玩家”关系对象。DeepSeek 只能把少量结论改写成一个标题和两句话。模型看不到双方完整计分板，也无法理解其他队友、敌方对位、目标时间、英雄类型和地图环境。

同时，当前提示词与校验器进一步压缩了表达空间：

- 生成温度为零，重复生成也容易得到近似句式。
- 正文被限制为固定句数和很短的篇幅。
- 禁止数字、比例和大量常见表达。
- 失败时的叙事方向由本地标签和关系对象提前确定。
- 角斗使用独立的极简事实包，只包含少量回合结果或资金排名。
- 前端只能展示标题和一段正文。

结果是模型没有足够上下文进行判断，只能稳定产出“封号 + 数据复述 + 安全比喻”的模板化文案。重构目标不是把相同提示词写得更毒，而是让 AI 获得理解整场比赛所需的信息，并让分析结论保持可核验。

## 2. 产品目标

重构后的 AI 锐评是一份短小、有梗、但有实际分析依据的中文赛后报告。它需要回答：

- 这场比赛主要赢在或输在哪里。
- 当前玩家在本局扮演了什么角色，应该获得什么表扬或承担什么责任。
- 哪些队友产生了最重要的正面或负面影响。
- 双方最明显的职责对位差距是什么。
- 目标时间、英雄特性、阵容环境和特殊地图是否改变了对计分板的解释。
- 哪个数据反差最值得形成一句有记忆点的锐评。

AI 必须分析双方完整数据后自行形成结论。本地不再预先决定带飞局、躺赢局、尽力局、背锅局、唯一主锅或唯一大爹。

## 3. 设计原则

### 3.1 本地准备案卷，AI 负责判断

本地负责确定性工作：

- 查询和整理比赛数据。
- 映射英雄、职责、地图和模式的稳定中文名称。
- 识别当前玩家，但只在模型输入中标记对应英雄记录。
- 计算队内排名、全场排名、职责汇总、比例、差值、参与率和赛季基准。
- 提供本场涉及的英雄类型、特殊英雄解释和特殊地图特性。
- 校验模型引用的数据和比较结论。

AI 负责需要综合判断与语言创造的工作：

- 判断整体比赛故事和主要胜负因素。
- 评价当前玩家。
- 分析关键队友和职责对位。
- 结合英雄与地图知识解释统计数据。
- 判断结论强度，区分直接事实和合理推断。
- 生成五个短区块的最终锐评。

### 3.2 完整不等于发送原始数据

“完整数据”指理解比赛所需的双方结构化计分板和客观派生指标，不发送原始 JSON、玩家名、BattleTag、账号 ID、对局 ID、GUID、路径或凭据。模型中的主体直接使用“我方/敌方 + 英雄名称”，例如“我方安娜”“敌方法老之鹰”。同队出现同英雄时使用稳定中文序号区分。

### 3.3 不强行找锅

失败不代表必须有唯一主锅，胜利也不代表当前玩家必须被夸。数据支持团队共同问题、阵容环境不利或双方表现接近的，AI 应明确如此表达。没有足够证据的区块或条目可以省略。

### 3.4 不把推断伪装成录像证据

最终计分板不能证明伤害具体打给了谁，也不能证明某次死亡来源、站位、技能使用和玩家主观意图。模型可以根据英雄类型和阵容形成职责推断，但必须使用与证据强度匹配的措辞。

## 4. 统一输入模型

普通对局和角斗使用同一个顶层 schema。角斗不是独立的缩水流程，而是在基础数据上附加少量角斗字段。

```json
{
  "schemaVersion": 2,
  "matchKind": "standard",
  "match": {},
  "currentPlayer": "我方安娜",
  "scoreboard": {
    "team": [],
    "opponent": []
  },
  "roleMatchups": [],
  "currentPlayerBaseline": {},
  "streak": {},
  "gameKnowledge": {},
  "arena": null
}
```

### 4.1 比赛信息

`match` 包含：

- 胜负。
- 游戏模式。
- 地图中文名。
- 我方与敌方比分。
- 对局时长。

字段缺失时明确使用 `null` 或省略可选字段，不以零值伪装缺失。

### 4.2 双方完整计分板

双方每名玩家包含：

```json
{
  "subject": "我方安娜",
  "isCurrentPlayer": true,
  "hero": "安娜",
  "role": "支援",
  "stats": {
    "kills": 7,
    "assists": 29,
    "deaths": 4,
    "damage": 5230,
    "healing": 17082,
    "mitigation": 0,
    "finalHits": 2,
    "objectiveTimeSeconds": 61,
    "healingReceived": 5834,
    "damageTaken": 9241
  },
  "derived": {
    "teamCompositeRank": 1,
    "matchCompositeRank": 2,
    "killParticipationRate": 0.82,
    "teamDamageShare": 0.14,
    "teamHealingShare": 0.47,
    "teamDeathShare": 0.09,
    "damagePerDeath": 1307.5,
    "healingPerDeath": 4270.5
  }
}
```

派生指标只能由已有可靠字段计算。不存在分母、样本不完整或指标不适用于该英雄时省略对应字段。

“综合排名”只是一项弱参考，不能继续作为自动主锅选择器。模型必须结合多维指标和游戏知识解释。

### 4.3 职责对位

`roleMatchups` 提供双方同职责的汇总与差值，不提供本地结论：

```json
{
  "role": "支援",
  "teamSubjects": ["我方安娜", "我方禅雅塔"],
  "opponentSubjects": ["敌方天使", "敌方朱诺"],
  "teamTotals": {
    "kills": 11,
    "assists": 48,
    "deaths": 9,
    "damage": 10420,
    "healing": 28650
  },
  "opponentTotals": {
    "kills": 17,
    "assists": 39,
    "deaths": 12,
    "damage": 15940,
    "healing": 24730
  },
  "deltas": {
    "kills": -6,
    "assists": 9,
    "deaths": -3,
    "damage": -5520,
    "healing": 3920
  }
}
```

AI 可以结合双方具体英雄解释差值，不能仅凭职责总量宣布一方“完败”。开放职责下按实际英雄职责分组；无法可靠映射职责的玩家保留在计分板中，但不进入职责汇总。

### 4.4 当前玩家赛季基准

`currentPlayerBaseline` 提供当前玩家同职责、当前赛季的可靠平均值或差异率。它用于判断本局是否明显偏离个人通常表现，不取代本场双方对比。

首版不新增英雄个人历史均值查询。后续如确有稳定数据和明确需求，再单独设计。

### 4.5 连续状态

继续发送当前对局之前的连续胜负次数及本局是否延续或终结连续状态。连续状态是可选的娱乐素材，不能压过本局计分板。

## 5. 角斗输入

角斗使用最后一个结构完整、比分可信的有效回合作为完整计分板来源，并保留普通对局的比赛信息、双方玩家、派生指标、职责对位、当前玩家基准和游戏知识。

角斗额外只发送：

1. 每回合胜负及回合结束后的比分。
2. 每名玩家的最终资金。

```json
{
  "matchKind": "arena",
  "arena": {
    "roundResults": [
      {"round": 1, "result": "loss", "scoreAfter": "0:1"},
      {"round": 2, "result": "loss", "scoreAfter": "0:2"},
      {"round": 3, "result": "loss", "scoreAfter": "0:3"},
      {"round": 4, "result": "win", "scoreAfter": "1:3"},
      {"round": 5, "result": "win", "scoreAfter": "2:3"},
      {"round": 6, "result": "win", "scoreAfter": "3:3"},
      {"round": 7, "result": "win", "scoreAfter": "4:3"}
    ],
    "finalWorth": {
      "我方安娜": 7050,
      "我方莱因哈特": 7380,
      "敌方法老之鹰": 7120
    }
  }
}
```

不发送逐回合计分板、逐回合资金轨迹、装备、异能、构筑变化或中间回合附加信息。

AI 可以识别让三追四、连续获胜、决胜回合和最终资金排名，也可以讨论最终资金与最终表现之间的反差；不能仅凭最终资金断言某个回合或整场胜负的原因。

## 6. 轻量比赛知识库

首版不实现阵容分析器，也不维护固定克制矩阵。应用随版本打包一份轻量、可审查的静态知识库，由 AI 自己结合本场阵容和计分板使用。

知识库只包含：

- 少量英雄类型及其通用统计解释。
- 单个英雄确有必要时的特殊覆盖。
- 少量会明显改变交火距离、拉扯速度或英雄发挥环境的特殊地图或子地图特性。

### 6.1 分类约束

- 每个英雄只有一个主要类型，必要时最多增加一个辅助类型。
- 每个职责只保留约两至三个真正影响数据解释的大类。
- 多个英雄共享相同统计解释时才建立类型。
- 单英雄特殊情况用覆盖项表达，不为其创建新类型。
- 不确定的英雄只保留职责，不编写推断规则。
- 分类不直接产生分数、主锅或职责结论。

初始分类骨架控制在：

- 坦克：狗坦、地面坦、消耗坦。
- 输出：枪位、狗位、阵地输出。
- 支援：治疗型、进攻型、功能型。

该骨架不是无需审查的硬编码结论。实施时必须获取当前完整英雄清单，逐个确定最小分类并生成可审查映射表；不清楚的条目留空。

### 6.2 类型画像

类型画像只解释统计数据，例如：

```json
{
  "archetype": "枪位",
  "statExpectations": {
    "damage": "通常应提供稳定的持续输出",
    "killsAndFinalHits": "需要判断伤害是否形成击杀转化",
    "deaths": "通常不以频繁深入敌阵作为正常解释",
    "context": "面对空中、远程或暴露目标时通常更有能力提供直接压力"
  }
}
```

```json
{
  "archetype": "狗位",
  "statExpectations": {
    "damage": "总伤害可能低于正面持续输出英雄",
    "killsAndFinalHits": "击杀参与、收割和关键目标压力更重要",
    "deaths": "切入风险较高，但频繁无收益阵亡仍是负面表现",
    "objectiveTime": "执行侧翼任务时目标时间较低不一定是问题"
  }
}
```

### 6.3 单英雄覆盖

类型无法准确解释的英雄可以提供覆盖项。例如：

- 禅雅塔：高伤害是正常且重要的支援贡献，治疗低于治疗型支援不能直接判定失职。
- 天使：个人伤害很低不构成负面证据，需要结合治疗、助攻、存活和敌方远程压力解释。
- 生命之梭：个人伤害通常较低；没有技能事件时不得判断生命之握质量。

实施阶段必须完成当前全部英雄的分类审查。单英雄特殊规则只写确认度高、会实质改变计分板解释的内容。

### 6.4 地图画像

地图画像只描述环境倾向，不生成自动结论。例如阿特利斯、伊里奥斯等短图可以记录转点快、拉扯快、交火距离偏短、高机动或近距离英雄更容易持续参与交火。

不同子地图差异明显时优先按子地图记录。应用只能识别到大地图而无法确认具体子地图时，不发送过于具体的视野、地形或交火距离断言。不确定或普通地图不强行填写画像。

### 6.5 运行时使用

每场只把本局涉及的类型画像、英雄覆盖和地图画像加入 `gameKnowledge`，不发送完整百科。模型自带知识只能补充措辞和一般推理，不能覆盖数据包中明确给出的解释边界。

首版不允许 DeepSeek 每场临时联网搜索。联网适合在维护期帮助更新知识库，运行时搜索会增加版本混乱、延迟、费用、不可复现性和外部故障面。

## 7. AI 分析任务

模型在生成最终报告前需要依次完成：

1. 阅读比赛信息、双方完整计分板和客观派生指标。
2. 比较双方同职责整体表现。
3. 结合英雄类型、单英雄覆盖、目标时间和地图环境重新解释统计数据。
4. 判断当前玩家的贡献与责任。
5. 识别最重要的正面贡献者、负面影响者和职责差距。
6. 找出最有节目效果的数据反差。
7. 按五区块 schema 输出，并为分析性结论附带证据引用。

提示词必须提醒模型：

- 高承伤不自动等于坦克失职。
- 高伤害不自动等于输出有效，需结合击杀、最后一击、参与率和存活。
- 治疗低不自动等于支援失职，需结合英雄类型和队伍承压。
- 目标时间较长可能解释部分战斗数据偏低，但不是万能免责项。
- 阵容中某英雄通常更适合处理一个威胁，只能形成职责推断；没有目标伤害或事件数据时不能声称其完全没有攻击该目标。
- 不得推断站位、技能命中、语音交流、故意送、摆烂或玩家主观意图。

## 8. 五区块输出

最终报告使用固定骨架和动态条目，默认总长度约三百五十至六百个汉字。数据不足时允许缩减内容，但本场判词、当前玩家评价和终审锐评仍需存在。

### 8.1 本场判词

- 一个简短、有梗的标题。
- 一句定义整场故事的总评。
- 不堆砌数字。

### 8.2 胜负手

- 两至三条主要胜负因素。
- 每条包含短标题、具体分析和证据引用。
- 胜利写“赢在哪”，失败写“输在哪”。
- 不把相关性写成未经证明的确定因果。

### 8.3 你这局

- 单独评价当前玩家。
- 顺序为定位结论、真实贡献、应承担的责任或局限。
- 不为了取悦用户强行甩锅，也不为了毒舌忽略真实贡献。

### 8.4 队友与对位

- 动态展示一至三项。
- 最多点名一名主要贡献者。
- 最多点名一名主要负面影响者。
- 最多展示一个最显著的职责对位或角斗走势。
- 同一个人不在多个条目中重复处刑。
- 数据不足时不凑满条目。

### 8.5 终审锐评

- 一句最有记忆点的收尾梗。
- 可以比分析区夸张，但不能冒充新的事实结论。

### 8.6 结构化输出

```json
{
  "verdict": {
    "title": "输出刷卡前排停机",
    "summary": "……"
  },
  "decisiveFactors": [
    {
      "title": "前排续航断裂",
      "commentary": "……",
      "claimType": "statistical_interpretation",
      "evidenceRefs": ["我方莱因哈特.stats.deaths"]
    }
  ],
  "currentPlayer": {
    "title": "不是主锅也没拿到免检章",
    "commentary": "……",
    "claimType": "statistical_interpretation",
    "evidenceRefs": ["我方安娜.stats.healing"]
  },
  "teamAndMatchups": [
    {
      "type": "positive_player",
      "title": "我方禅雅塔",
      "commentary": "……",
      "claimType": "direct_fact",
      "evidenceRefs": ["我方禅雅塔.stats.damage"]
    }
  ],
  "closingRoast": "……"
}
```

`claimType` 取值：

- `direct_fact`：数据直接证明。
- `statistical_interpretation`：由多个指标共同解释。
- `game_context_inference`：由英雄或地图知识与数据共同推断。

前端不展示英文类型，但校验器根据类型控制允许的措辞强度。

## 9. 文风：事实优先的冷面损友

目标风格参考 Grok 给人的“直接、机智、犀利、少公关腔”体验，但提示词不要求模型扮演或自称 Grok。文风必须被拆成独立、可测试的行为规则。

### 9.1 人格

- 像真正懂《守望先锋》的损友复盘。
- 事实优先，结论直接，不写客服、公关或教练套话。
- 擅长一本正经地描述数据中的荒谬反差。
- 可以评价当前玩家和队友的本局表现，不必讨好用户。
- 嘲讽行为、数据结果和职责完成情况，不攻击人格、智力、身份或现实生活。
- 不说教，不解释笑话。

### 9.2 笑点来源

优先从本局独有反差制造包袱：

- 高伤害、低击杀转化。
- 高治疗、全队仍高阵亡。
- 高承伤、低前排收益。
- 高资源占用、低产出。
- 高目标时间与偏低战斗数据的职责错位。
- 某职责数据领先但比赛失败。
- 当前玩家表现突出却输掉比赛，或表现普通却被队友抬赢。
- 角斗回合走势与最终资金、最终表现之间的反差。

如果一句话换到大多数其他对局仍成立，就视为模板化套话，应重写。

### 9.3 节奏

- 本场判词：强梗。
- 胜负手：事实为主，每条最多一个轻梗。
- 你这局：直接、诚实，中等锐度。
- 队友与对位：分析为主，只选择一处重点锐评。
- 终审锐评：最强收尾梗。

不要求每个区块、每句话都搞笑。

### 9.4 禁止写作习惯

- 不以“从数据来看”“综合来看”“整体而言”开头。
- 不使用“表现较为稳定”“节奏掌控良好”“压制力十足”“已经尽力”“这锅不背”等公关式套话。
- 不反复使用墙、定海神针、局长、守门员、后勤部长等万能封号。
- 不连续堆砌网络流行语。
- 不在同一份报告混用多套比喻体系。
- 不为了玩梗篡改事实。

### 9.5 正反例

提示词加入少量机制不同的正反例，帮助模型理解“具体、有梗”和“空泛套话”的差别。正例覆盖反差、角色错位、冷面描述和任务未完成等机制，不能全部使用职场比喻，也不能让模型照抄示例。

## 10. 模型调用

首版继续使用应用内部配置的 `deepseek-v4-flash`，让模型先综合分析再输出最终结构化报告。初始请求参数固定为：

```json
{
  "model": "deepseek-v4-flash",
  "thinking": {
    "type": "enabled"
  },
  "reasoning_effort": "high",
  "temperature": 0.8,
  "max_tokens": 4000,
  "response_format": {
    "type": "json_object"
  },
  "stream": false
}
```

模型名和思考配置保留为内部版本化常量，不进入用户设置。若官方 API 在实施时改变参数语义，实施计划必须依据当时官方文档更新整组参数和对应提示词版本，不能静默回退到非思考模式或零温度。

生成仍采用单次主请求，不拆成“分析一次、写作一次”两次计费调用。输出长度上限按五区块 JSON 调高，避免截断。

创造性不再通过 `temperature: 0.0` 锁死。合成样本需要验证 `temperature: 0.8` 下的事实稳定性和文案多样性；如果验证不合格，应通过新的设计修订调整参数，而不是在实现中自行漂移。实现不依赖已废弃模型别名。

## 11. 证据与校验

### 11.1 必须带证据的内容

- 胜负手。
- 当前玩家评价。
- 队友正负面影响。
- 职责对位。
- 角斗回合走势与最终资金结论。
- 最高、最低、领先、落后和排名等可验证断言。

标题中的比喻和不冒充事实的终审锐评可以不带证据。

### 11.2 硬校验

本地校验：

- JSON schema 和区块数量。
- 所有主体和 `evidenceRefs` 都存在于请求数据。
- 数字与被引用字段一致。
- 排名、最高、最低、领先和落后等断言可由本地数据复核。
- 当前玩家身份未被混淆。
- 角斗回合与最终资金引用正确。
- `claimType` 合法，并且推断性结论没有使用伪装成直接证据的措辞。
- 不出现未提供的玩家、英雄、地图、数据字段或身份信息。
- 不出现人身攻击、身份攻击、仇恨表达或凭据内容。
- 单区块和总长度符合上限。

### 11.3 删除或放宽旧限制

- 不再禁止所有数字。
- 不再要求恰好两句话。
- 不再要求只引用预选的三至四条事实。
- 不再要求必须存在一个关系对象。
- 不再要求失败时必须向队友甩锅。
- 不再用大范围词语黑名单压制正常比喻。
- 不把“是否足够有趣”交给关键词校验器判断。

### 11.4 修正与失败

一次用户操作最多包含：

1. 一次主生成。
2. 一次有限修正。

局部问题只返回匿名位置和错误类型，例如“`teamAndMatchups[1]` 引用了不存在的证据字段”，要求保留其他区块。JSON 无法解析、大量结论无证据、出现未提供主体、攻击性内容或结构完全错误时整份修正。

第二次仍失败则返回既有可恢复错误，不保存部分结果，不增加多轮自动尝试。

## 12. 前端展示

成功态从标题加单段正文改为五区块短报告：

```text
本场判词
标题 + 一句总评

胜负手
两至三条原因

你这局
一段当前玩家评价

队友与对位
一至三条关键人物、职责对位或角斗走势

终审锐评
一句收尾梗
```

视觉继续遵循根目录 `design.md`：使用一个连续表面、文字层级、留白和细分隔线，不把每条内容做成独立白色卡片，不引入新的品牌色、字体、圆角或阴影语言。

重新生成保留，成功后用新结果原子替换旧结果；生成失败时继续显示旧结果和行内错误，不先清空已有内容。

## 13. 存储与兼容

新结果需要保存完整结构化报告，而不是只保存 `award` 和 `commentary`。SQLite 使用幂等前向迁移增加：

- 报告 JSON。
- 报告 schema 版本。
- 输入 schema 版本。
- 知识库版本。
- 提示词版本。
- 模型和生成时间继续保留。

迁移不得重写或删除历史锐评。旧记录继续按旧标题和正文展示，并提供“重新生成”；重新生成成功后写入新报告。新旧记录读取逻辑必须可区分，升级库测试覆盖旧表、迁移后旧记录和新记录。

知识库或提示词升级不自动使已有成功报告失效。用户主动重新生成时使用当前版本并覆盖本场旧结果。

## 14. 测试与验收

### 14.1 数据包测试

- 普通对局包含双方完整计分板，而不是三至四条预选事实。
- 字段缺失时不伪造零值。
- 职责汇总和派生指标计算正确。
- 当前玩家只通过英雄主体标记进入模型数据。
- 不包含玩家名、BattleTag、账号 ID、对局 ID、GUID、原始 JSON、路径或凭据。
- 角斗包含最后有效回合完整数据、每回合胜负和最终资金，不包含逐回合计分板、构筑或资金轨迹。

### 14.2 知识库测试

- 当前完整英雄清单均经过分类审查。
- 每个英雄至多一个主要类型和一个辅助类型。
- 特殊英雄覆盖能够替代通用类型的错误解释。
- 不确定条目允许为空且不阻塞生成。
- 只发送本局涉及的知识。
- 特殊地图按可识别粒度匹配，不把子地图结论错误套到整张地图。

### 14.3 分析样本

使用纯合成对局覆盖：

- 敌方远程输出压缩我方天使生存环境。
- 我方枪位是主要对空压力来源，但敌方法老之鹰仍形成高影响；结论必须是职责推断，不能声称其完全没有攻击法老之鹰。
- 禅雅塔高伤害低治疗不被简单判定失职。
- 天使、生命之梭低伤害不被当作负面证据。
- 当前玩家目标时间高，战斗数据偏低得到合理解释，但目标时间不成为万能免责项。
- 坦克高承伤分别对应有效推进和低收益承伤两种不同结论。
- 高伤害低击杀转化。
- 支援治疗领先但队伍高阵亡。
- 没有可靠唯一主锅的接近比赛。
- 当前玩家真实背锅，报告不强行向队友转移责任。
- 角斗让三追四和普通胜负序列。
- 最终资金排名与表现反差，但不产生未经证明的资金因果。

### 14.4 文风验收

建立多场合成黄金样本和禁用模式断言：

- 五区块不重复同一结论。
- 至少一个笑点来自本局独有数据反差。
- 不出现公关式套话和万能封号。
- 不连续堆梗，不让每句话都承担笑点。
- 当前玩家、队友和敌方使用一致的事实标准。
- 同一输入重新生成时，核心事实判断可接近，但标题、比喻和收尾应有明显变化。
- 文案不攻击人格，不推断故意送、摆烂或交流行为。

文风无法仅靠字符串断言完全验证。实施验收需要固定一组合成数据，进行人工盲评，至少检查准确性、具体性、犀利度、幽默度、重复感和公平性。

### 14.5 工程验证

- Rust 素材、知识筛选、请求、校验、存储和升级库测试。
- React 五区块成功态、旧记录兼容、重新生成和错误保留测试。
- 前端构建与后端测试。
- `git diff --check`。
- 不使用真实凭据、真实玩家数据或本地隐私数据进行调试与截图。

## 15. 非目标

本次不包含：

- 运行时联网搜索游戏知识。
- 固定英雄克制矩阵。
- 自动阵容分析器或本地主锅判定器。
- 逐回合角斗详细复盘。
- 装备、异能或构筑分析。
- 伤害目标分布、死亡来源、站位、技能命中或团战时间线推断。
- 多种用户可选文风。
- 长篇专业教练报告。
- 自动生成、分享图片或多轮追问。

## 16. 成功标准

重构成功需要同时满足：

- AI 能看到双方完整对局，而不是只重组三至四条本地结论。
- 普通与角斗共享相同分析能力，角斗仅增加最终回合、回合胜负和最终资金。
- 英雄类型、特殊英雄和特殊地图能实质改变统计解释。
- 报告稳定回答胜负原因、当前玩家、队友影响和职责对位。
- 结论可以追溯到输入数据或明确的游戏上下文推断。
- 文案直接、有梗、犀利，但不靠人身攻击制造刺激。
- 不再重复当前“封号 + 数据复述 + 安全套话”的固定模板。
