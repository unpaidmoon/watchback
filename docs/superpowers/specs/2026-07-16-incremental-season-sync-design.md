# OWStatsLocal 安全增量赛季同步设计

日期：2026-07-16

## 1. 背景

当前赛季同步每次都会：

1. 从第 1 页开始抓取普通模式与角斗模式的全部对局列表，直到遇到空批次。
2. 对本次列表中的每一场对局重新请求详情。
3. 将完整 payload 写入本地 JSON，并幂等写入 SQLite。

重复同步不会在 SQLite 中制造重复对局，但详情网络请求量仍与完整赛季对局数成正比。赛季进行越久，重复同步耗时越长。

本设计将普通“同步/更新”改为安全增量模式。第一阶段只减少详情请求，不依据未经验证的页数、时间戳或本地水位提前停止列表分页。

## 2. 目标

- 第一次同步某赛季时保持完整抓取行为。
- 后续同步仍完整校验上游列表，但只请求：
  - 本地数据库不存在的新对局详情。
  - 本地已有列表记录但缺少详情的对局详情。
- 已有完整详情的对局不得重复请求详情。
- 重复执行增量同步必须幂等。
- 增量同步不得缩小既有赛季统计、清空未涉及的玩家索引或覆盖掉完整本地快照。
- 保持当前赛季无显式 `season` 参数优先、指定赛季回退的请求行为。
- 普通模式和角斗模式继续使用各自的列表与详情接口。
- 所有新增持久化、错误和诊断信息继续满足递归脱敏要求。

## 3. 非目标

第一阶段不包括：

- 根据“连续一页或两页都是旧数据”提前停止分页。
- 假设上游每页固定返回某个数量。
- 假设上游跨页严格按 `beginTs` 倒序排列。
- 使用上游尚未证实存在的游标、增量时间或 `since` 参数。
- 定时后台同步、自动轮询或“一键同步全部赛季”。
- 删除本次上游列表未返回、但本地仍然存在的历史对局。

提前停止分页只能作为后续独立优化。它必须建立在真实接口的非敏感分页诊断和明确测试证据上。

## 4. 核心术语

- **列表已存在**：`matches` 表中已有相同 `match_id` 和目标 `season`。
- **详情完整**：`match_details` 表中已有该 `match_id` 的有效详情行。
- **新对局**：上游列表返回、但本地目标赛季不存在该 `match_id`。
- **缺失详情对局**：本地存在列表记录，但不存在对应详情行。
- **详情请求集合**：新对局与缺失详情对局的去重并集。
- **完整列表校验**：仍然从第一页抓到空批次，不做旧页提前停止。

## 5. 方案选择

### 5.1 已选方案：完整列表校验，详情增量抓取

每次同步仍抓取完整列表，因此不会因为未验证的分页排序假设漏掉后续页的新对局。列表抓取完成后，后端用本地数据库判断详情请求集合，只对该集合调用详情接口。

该方案不能消除列表分页耗时，但通常可以消除绝大多数逐场详情请求，并且不需要依赖上游未承诺的分页顺序。

### 5.2 暂不采用：固定旧页数量后停止

“连续两页都是旧数据”没有现有接口契约或真实测试依据。接口只接受 `page`，不接受本地可控的 `pageSize`；现有 mock 数据也不能证明生产接口的页容量与跨页稳定性。因此第一阶段不得引入固定页数阈值。

### 5.3 暂不采用：仅按最新时间戳停止

本地在完整抓取结束后按 `beginTs` 排序，不等于上游分页本身严格有序。只凭时间水位提前停止可能漏掉延迟写入、排序抖动或跨模式落在后续页的新对局。

## 6. 架构边界

增量行为分为四个明确阶段：

1. **本地同步状态读取**
   - 从 SQLite 读取目标赛季已有 `match_id`。
   - 同时读取哪些 `match_id` 已有详情。
   - 不读取或输出凭据、玩家隐私 ID 或未脱敏原始数据。

2. **完整列表抓取**
   - 保持现有普通模式、角斗模式、当前赛季候选参数和空批次停止行为。
   - 对列表结果按 `match_id` 去重。
   - 不在这一阶段请求详情。

3. **增量详情抓取**
   - 计算 `新对局 ∪ 缺失详情对局`。
   - 仅对该集合调用普通或角斗详情接口。
   - 继续使用现有限速、并发上限、429 重试和脱敏错误。

4. **增量事务落库与完整快照重建**
   - 更新本次列表返回的对局。
   - 只更新本次成功抓取的详情及其派生玩家索引。
   - 从数据库重新计算赛季统计。
   - 使用当前抓取元数据与数据库中的完整赛季记录重建脱敏 JSON 快照。

列表抓取与详情抓取应继续共享同一条正式同步路径，避免命令行导出与桌面同步产生协议漂移。

## 7. 数据流

```text
用户点击同步 Sxx
  -> 校验当前账号登录目标
  -> 查询 SQLite：已有列表 ID、已有详情 ID
  -> 完整抓取各模式列表直到空批次
  -> 对列表按 match_id 去重
  -> 计算新对局和缺失详情
  -> 仅请求这些对局的详情
  -> 单事务增量写入 SQLite
  -> 查询 SQLite 生成真实赛季总数
  -> 重建并覆盖脱敏完整赛季 JSON
  -> 清理前端对局页缓存
  -> 返回中文同步摘要
```

第一次同步时已有集合为空，因此详情请求集合自然等于全部列表，实现与当前完整同步等价的行为，不需要单独维护第二套首同步算法。

## 8. 列表抓取规则

- 普通模式继续抓取 `sport`、`leisure`。
- 角斗模式继续抓取 `QuickFight`、`LeisureFight`、`SportFight`。
- 每个模式仍从第 1 页开始。
- 当前赛季继续先不传显式赛季参数；没有有效数据时再使用显式赛季参数回退。
- 仍以空批次作为分页结束条件。
- 列表结果中的重复 `match_id` 在进入详情集合计算前去重。
- 列表抓取失败时不得进入数据库写入阶段，也不得破坏上一次成功同步的数据。

本阶段允许保留现有批量并发分页策略，但测试必须证明无论响应完成顺序如何，所有已请求页面都会被处理。

## 9. 详情集合与请求规则

### 9.1 集合计算

对每条去重后的上游列表记录：

- 本地无 `match_id`：标记为新对局并请求详情。
- 本地有 `match_id`，但无 `match_details`：标记为详情修复并请求详情。
- 本地同时有列表与详情：不请求详情。

详情集合按 `match_id` 再次去重。详情接口根据列表记录中的对局种类选择普通或角斗端点。

### 9.2 详情失败

- 单场详情失败不终止整个赛季同步。
- 新对局列表仍可写入，详情保持缺失状态。
- 缺失详情修复失败时继续保持缺失状态。
- 错误记录必须递归脱敏。
- 下次增量同步会再次把缺失详情纳入请求集合。

### 9.3 不刷新已有完整详情

第一阶段默认不重新请求已有完整详情。若未来确认上游会事后修正详情，应另行设计“刷新最近若干场”或手动完整刷新能力，不能偷偷扩大本阶段范围。

## 10. SQLite 写入规则

### 10.1 对局列表

本次上游返回的列表记录继续按 `match_id` 幂等 upsert。已有记录可以刷新列表级字段，新记录正常插入。

当本次没有新详情时，列表 upsert 不得把数据库中已有的以下信息降级为空值或零：

- `match_kind`
- `bucket`
- `duration_sec`
- 依赖详情得出的其他现有投影字段

实现时应显式保留已有详情派生值，或从数据库已有详情计算更新值；不能继续把“本次 payload 没带详情”解释为“详情不存在”。

### 10.2 对局详情

只 upsert 本次成功抓取的详情。没有重新请求的已有详情保持不变。

### 10.3 玩家索引

现有整季删除 `match_players` 和 `arena_match_players` 后仅用本次详情重建的行为不适用于增量 payload。

增量同步必须：

- 仅删除本次成功详情对应 `match_id` 的旧玩家索引。
- 用该详情重建对应普通或角斗索引。
- 未请求或请求失败的对局索引保持不变。

第一次同步因为所有详情都是新详情，最终结果仍等价于完整重建。

### 10.4 同步错误

错误状态按被尝试的 `match_id` 定向更新：

- 请求成功：清除该赛季、该 `match_id` 的旧详情错误。
- 请求失败：替换或 upsert 该赛季、该 `match_id` 的最新脱敏错误。
- 本次未尝试的对局：保留原错误，等待未来修复。

不得再因为一次增量同步而无条件删除整个赛季的全部错误记录。

### 10.5 赛季统计

同步完成后，从 SQLite 按目标赛季重新查询：

- 对局总数。
- 详情总数。
- 当前缺失详情数。
- 普通与角斗数量。
- 最新同步时间。

不得使用本次新增数量覆盖赛季总量。同步摘要应同时区分：

- 上游列表看到的对局数。
- 新增对局数。
- 请求详情数。
- 成功新增或修复详情数。
- 详情失败数。
- 数据库当前赛季总对局数。

## 11. 本地 JSON 快照

现有 `local_s{season}_full_season.json` 表示完整本地赛季快照。增量 payload 不能直接覆盖该文件。

同步事务成功后：

1. 从 SQLite 读取该赛季完整的已脱敏列表与详情。
2. 合并本次最新的 `profile_card`、`count_info` 和列表页元数据。
3. 写入临时文件。
4. 成功序列化并完成脱敏检查后，以原子替换方式更新正式快照。

若快照写入失败：

- SQLite 已提交的数据不得回滚成损坏状态。
- 同步结果应明确报告“数据库更新成功，但本地快照更新失败”。
- 不得留下半写入 JSON。

快照不得恢复已被 SQLite 持久化边界删除的 token-like 字段。

## 12. 进度与用户反馈

用户可见文本保持中文。建议进度阶段：

1. `正在检查本地数据`
2. `正在获取赛季对局列表`
3. `发现 N 场新对局，M 场缺少详情`
4. `正在获取详情 X / Y`
5. `正在更新本地数据库`
6. `同步完成`

无新对局且无缺失详情时显示：

```text
已是最新数据，共校验 N 场对局，无需重新获取详情。
```

有新增或修复时显示：

```text
更新完成：新增 N 场，补全 M 场详情，当前赛季共 T 场。
```

错误摘要不得包含对局隐私 ID、凭据或 token-like 内容。

## 13. 非敏感诊断指标

第一阶段记录或返回以下汇总指标，为后续“安全提前停止分页”提供依据：

- 每个模式请求的页数。
- 每页返回条数。
- 每页新增、已有、缺失详情数量。
- 每页最早与最晚 `beginTs`。
- 列表阶段、详情阶段、落库阶段耗时。

诊断信息不得包含：

- 原始 `match_id`。
- BattleTag、玩家 ID 或玩家显示名。
- token、customer token、cookie、authorization 或 credential。
- 原始列表页和原始详情 JSON。

诊断指标默认仅用于本地调试和测试，不新增遥测上传。

## 14. 后续提前停止的准入条件

只有同时满足以下条件，才能另开设计引入提前停页：

1. 多次真实同步的非敏感诊断证明每个相关模式的分页顺序稳定。
2. 明确验证单页容量及空页行为。
3. 验证新对局、延迟写入对局和排序相同时间戳时的跨页行为。
4. 测试包含“前面页面全是旧数据，但后续页面出现新数据”的反例。
5. 停止规则不是未经说明的魔法常量，并具有保守回退。
6. 用户始终能触发不提前停止的安全校验路径。

第一阶段不得预埋默认值为 `2` 的连续旧页阈值。

## 15. 测试策略

### 15.1 列表与详情请求

- 空数据库首次同步：所有列表对局都请求详情。
- 已有完整赛季再次同步：列表仍翻到空批次，详情请求次数为零。
- 后续页出现一场新对局：必须发现并只请求这一场详情。
- 已有对局缺少详情：只请求缺失详情。
- 同一 `match_id` 跨模式或跨页重复：只请求一次详情。
- 普通与角斗详情分别调用正确端点。
- 当前赛季继续验证无显式赛季参数优先与显式赛季回退。
- 详情并发、限速和 429 重试行为保持不变。

### 15.2 增量落库

- 重复同步不增加重复 `matches` 或 `match_details`。
- 无新详情时，已有 `match_kind`、`bucket`、`duration_sec` 不得降级。
- 新详情只重建对应对局的玩家索引。
- 未请求详情的旧对局玩家索引保持不变。
- 详情失败不会删除旧索引或其他对局错误。
- 详情修复成功后清除对应错误。
- 赛季统计来自数据库总量，不是本次增量数量。
- 后续同步上游列表为空或失败时，不得清空既有赛季数据。

### 15.3 快照与隐私

- 增量同步后完整 JSON 同时包含旧对局与新对局。
- 快照替换失败不会留下截断文件。
- JSON、SQLite、同步摘要、错误和诊断指标不包含 token-like 字段。
- 诊断输出不包含原始对局 ID 或玩家隐私标识。

### 15.4 性能验收

构造一个本地已有大量完整详情、上游只新增少量对局的 fixture：

- 列表请求数与完整列表校验一致。
- 详情请求数严格等于“新对局数 + 缺失详情数”去重后的数量。
- 第二次无变化同步的详情请求数为零。
- 同步摘要明确报告列表校验量和详情请求量。

性能验收以详情请求数量为第一阶段硬指标，不承诺未经测量的固定总耗时比例。

## 16. 验收标准

第一阶段完成需同时满足：

1. 普通同步默认执行安全增量模式。
2. 首次同步仍能得到完整赛季数据。
3. 重复同步已有完整赛季时不再请求任何对局详情。
4. 新对局和缺失详情能在任意列表页被发现并抓取。
5. 没有基于固定一页、两页或时间水位的提前停止。
6. 旧详情、玩家索引、同步错误和赛季统计不会被增量 payload 误删或缩小。
7. 完整本地 JSON 快照保持完整且递归脱敏。
8. 后端测试、前端同步相关测试、构建和 `git diff --check` 通过。
9. 验证报告明确列出实际详情请求次数，并说明未执行的真实上游验证。
