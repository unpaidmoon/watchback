# 生涯 MMR v4 表现证据评分设计

日期：2026-07-21

状态：待用户审阅

## 1. 背景与结论

生涯 MMR v3 完成了模型版本、事务激活、回滚、训练产物和解释接口等工程框架，但最终个人表现模型不合格：一级学习候选为 0，三级所谓百分位模型没有在运行时使用真实百分位基线，三个职责得到近似相同的正向权重，死亡和职责核心统计没有实际影响，修正近乎只奖不罚且幅度不可感知。训练投影与正式重放还使用了不同的身份和表现数据路径，导致角斗数据进入训练却没有进入正式 MMR，普通比赛的正式表现特征也为空。

v4 不继续放宽 v3 门槛，也不以“必须产生非零模型”为成功标准。v4 采用以下路线：

1. 保留 v2 作为发布基线和回滚版本。
2. 使用成熟评分算法作为胜负基础层挑战者，但不预设一定替换 v2。
3. 参考 TrueSkill 2，将个人统计视为本场隐藏表现的附加证据，而不是直接按原始统计奖励 MMR。
4. 只用现有两个账号学习稳健分布基线，不从两个账号拟合复杂自由权重。
5. 用顺序重放预测下一场结果，验证个人表现证据是否改善未来技能估计；禁止用本场统计预测本场已知结果作为主要晋级指标。
6. 任一实验超过 30 分钟立即终止并报告，不进入无价值的高次数 bootstrap。

技术评估结论是：当前数据足以支持受限版 v4，但不足以支持完整 TrueSkill 2。v4 必须明确标注为 `TrueSkill2-inspired evidence rating`，不得声称是 Microsoft TrueSkill 2 的完整实现。

## 2. 目标

v4 的目标是生成一个本地、确定性、可解释的生涯技能估计，使胜负和对局强度保持主导，同时让稳定、相对同类基线的个人表现对单场变化产生可感知且对称的影响。

具体目标：

- 胜、平、负、对局强度、模式权重和不确定性继续决定基础变化。
- 高于同职责、同环境、同模式基线的表现产生正证据；低于基线产生负证据；普通表现接近 0。
- 胜局中的差表现减少加分，败局中的优秀表现减少扣分，但个人表现不得翻转胜负基础变化方向。
- 坦克、输出、支援使用不同且符合职责语义的特征组合。
- 普通与角斗环境不共享原始统计基线。
- 训练和正式重放使用完全相同的投影、归一化和评分代码。
- 模型只有在下一场预测、分布、公平性、端到端运行和性能门禁全部通过后才能激活。
- 单轮离线实验在 release 构建下最多运行 30 分钟，并持续输出匿名进度。

## 3. 明确不做

- 不完整复刻 TrueSkill 2 的 Infer.NET 因子图、全体玩家联合后验或全模式协方差训练。
- 不长期保存队友或对手的个人 MMR 档案。
- 不把两个本地账号视为足以证明跨玩家泛化。
- 不从两个账号自由搜索大量特征组合、职责权重或非线性模型。
- 不把同一场比赛的个人统计对本场胜负拟合优度作为主要上线证据。
- 不为了保证上线而发布固定非零、单边奖励或没有实际基线的兜底模型。
- 不删除或改写 v2、v3 历史模型及事件。
- 不读取、记录或发布账号身份、BattleTag、比赛 ID、文件路径、原始 JSON、SQLite 内容或凭据。

## 4. 当前数据能力与限制

现有匿名聚合包含 2 个账号、5 个赛季、6,405 条投影和 5,542 条可用表现记录。职责记录为坦克 1,684、输出 1,681、支援 3,040。可用表现记录按模式分布为：职责竞技 416、职责快速 3,564、开放竞技 276、开放快速 175、角斗竞技 1,072、角斗快速 39。

这些数据支持：

- 职责快速的独立验证。
- 角斗竞技的独立验证。
- 普通环境和角斗环境分别建立职责级稳健基线。
- 五个赛季的时间前向验证。
- 两账号留一诊断，但不能据此声称普遍泛化。

这些数据不支持：

- 角斗快速独立校准。
- 每个英雄、模式、赛季、胜负组合都建立独立参数。
- 完整团队 TrueSkill/Weng-Lin 所需的所有玩家历史评分。
- 从数据自由学习大量职责特征系数。

普通环境中，支援的治疗、助攻、伤害和死亡覆盖较好；输出的伤害、死亡和最终一击可用，但助攻覆盖明显较低；坦克的伤害、死亡、最终一击和助攻可用，但普通模式缺少可靠减伤投影，目标时间覆盖也不足。角斗环境中的击杀、助攻、死亡、伤害、治疗、减伤、承伤和目标时间覆盖相对完整。

## 5. 总体架构

v4 分为五个相互独立的组件：

1. `UnifiedProjection`：从 SQLite 和详情 JSON 生成统一匿名比赛输入。
2. `OutcomeRatingChallenger`：比较现有 v2、Glicko-2 和 TrueSkill 风格虚拟对手基础层。
3. `PerformanceBaseline`：建立无未来泄漏的职责化稳健统计基线。
4. `PerformanceEvidence`：把当前比赛统计转换为本场隐藏表现证据和 MMR 修正。
5. `V4ReplayAndActivation`：执行顺序重放、验证、事务激活、查询与回滚。

组件之间只传递结构化 DTO。训练不得直接读取运行时事件表中的 v3 表现修正；正式重放不得使用与训练不同的特征提取分支。

## 6. 统一数据投影

### 6.1 单一实现

训练、评估、影子重放和正式重放必须调用同一个 `UnifiedProjection`。同一个已导入比赛在四条路径中必须产生相同的：

- `role`
- `modeFamily`
- `result`
- `durationSec`
- `dataQuality`
- `teamStrength`
- `opponentStrength`
- `rankCoverage`
- `performanceFeatures`
- `inputHash`

不允许训练使用 `TrainingRow` 的完整特征，而正式 `MmrMatchInput` 写入空 `performanceFeatures`。

### 6.2 身份解析

普通比赛继续使用 `match_players` 中恰好一条 `is_current_player=1` 的记录。角斗比赛必须使用当前账号 manifest 中的 BattleTag，在 `arena_match_players.player_name` 中查找同场恰好一条匹配记录并取得 `bnet_id`。零匹配或多匹配时整场表现数据不可用，不得回退到第一名玩家；如果胜负、职责和时长仍可靠，可以保留 outcome-only 输入。

BattleTag 只作为内存中的身份解析参数，不写入 DTO、日志、报告、artifact 或数据库新字段。

### 6.3 特征 DTO

统一投影至少包含：

```text
finalHit
kill
assist
death
damage
healing
mitigation
damageTaken
healingTaken
availableTeamHealing
objectiveTimeSec
```

缺失值保持缺失，不填 0。无效、负数或非有限值按字段级缺失处理。整场缺少足够证据时只计算胜负基础分。

### 6.4 角斗回合

角斗继续使用排序后最后一个结构有效的最终快照，不累加多个累计回合。正式重放必须通过合成测试证明 `match_players` 为 0 行时仍可使用 `arena_match_players` 唯一身份生成角斗事件。

## 7. 胜负基础评分挑战赛

### 7.1 候选

基础层只比较三个候选：

- `B0 current-v2`：当前自适应 K 值、模式权重和 sigma 机制。
- `B1 glicko2-virtual-opponent`：使用 Rust `skillratings` 的 Glicko-2，当前职责玩家对阵由对手队伍段位强度构造的虚拟对手。
- `B2 trueskill-virtual-opponent`：使用 Rust `skillratings` 的 TrueSkill，当前职责玩家与虚拟双方强度进行两方更新。

首轮不运行完整团队 Weng-Lin。当前数据库只观察与本地账号共同出现的玩家片段，无法可靠维护全体玩家长期评分；把这些不完整局部历史当作完整团队技能会制造偏差。

### 7.2 虚拟对手规则

双方段位覆盖达到既定完整性要求时，使用 `teamStrength` 和 `opponentStrength` 构造对局先验。覆盖不足时使用中性预期 `0.5`，并降低该场对基础算法比较的证据权重。不得凭单侧段位推造另一侧强度。

### 7.3 选择指标

所有候选按时间顺序重放。对比赛 `t` 的预测必须只使用 `t` 之前的数据；比赛 `t` 完成后才允许更新评分。主要指标是下一场结果的：

- Brier score
- log loss
- ECE
- 逐职责和逐模式校准
- 评分波动和单场封顶率

新基础算法只有在聚合 Brier 或 log loss 至少一项改善、另一项不显著恶化、ECE 恶化不超过 `0.01`，且至少 3/5 个时间前向折不差于 B0 时才可替换 B0。没有挑战者通过时，v4 保留 B0；这不阻止继续评估个人表现层。

## 8. 稳健表现基线

### 8.1 统计转换

计数和累计值先按实际参与时长转换为每 10 分钟统计。时长无效时整场表现证据不可用。每项统计使用训练窗口内的中位数和 MAD 转为稳健 z-score，并截断在 `[-3, 3]`。

正向指标使用：

```text
z = clip((valuePer10 - median) / max(1.4826 * MAD, floor), -3, 3)
```

负向指标如死亡使用相反方向。缺失项不进入分子或分母，不得把缺失解释为平均表现。

### 8.2 分层键

基线按以下优先级查找：

1. `role + environment + mode + hero + resultClass`
2. `role + environment + mode + resultClass`
3. `role + environment + resultClass`
4. `unavailable`

`environment` 只能是 `ordinary` 或 `stadium`，两者禁止交叉回退。`resultClass` 为 win、loss、draw；把胜局与胜局、败局与败局比较，降低统计对胜负结果的重复计价。

最低样本要求：英雄层 50、模式结果层 100、环境结果层 50。未达到要求时按层级回退；没有同结果类别基线时该场为 outcome-only，不得跨 win/loss 基线回退。基线状态随时间顺序重放在线更新：当前比赛先用此前状态评分，评分完成后才把当前统计加入基线。验证、影子重放和正式重放都遵守这一顺序，禁止全量未来数据泄漏到历史事件。

### 8.3 赛季变化

新赛季优先继承上一赛季环境基线并增加不确定性；累计达到最低样本后再建立当前赛季校准。不得为样本很少的新赛季强行创建独立英雄基线。

## 9. 职责表现证据

### 9.1 候选模板

个人表现层只比较三个预先定义的模板，不执行自由特征搜索：

- `P0 outcome-only`：不使用个人统计，作为对照。
- `P1 core-evidence`：只使用参与、最终一击、死亡/生存等高覆盖公共证据。
- `P2 role-balanced-evidence`：加入职责核心特征和目标贡献。

角斗环境额外允许 `P3 stadium-resource-evidence`，在 P2 上加入覆盖可靠的减伤、治疗和资源转化证据。普通环境不得因为角斗有减伤字段就推造普通坦克减伤。

### 9.2 初始固定权重

权重是产品先验，不从两个账号自由拟合。每个模板内部归一化为 1。

普通坦克 P2：

- 生存/死亡：30%
- 击杀与助攻参与：25%
- 伤害转化：25%
- 目标时间：20%，字段缺失时按其余特征重新归一化

普通输出 P2：

- 最终一击：25%
- 伤害转化：25%
- 生存/死亡：25%
- 击杀与助攻参与：15%
- 目标时间：10%

普通支援 P2：

- 治疗：30%
- 生存/死亡：25%
- 助攻参与：20%
- 目标时间：15%
- 有效伤害：10%

角斗职责模板使用相同职责方向，但坦克可将 25% 分配给减伤，支援可将 10% 分配给经过验证的资源效率。`damageTaken`、`healingTaken` 和 `availableTeamHealing` 不得单独作为“越高越好”指标，只能进入方向明确、验证通过的资源转化派生项。

### 9.3 可靠度与隐藏表现证据

每个特征的有效权重为：

```text
effectiveWeight = productWeight
                * baselineSampleReliability
                * fieldCoverageReliability
                * dataQuality
```

其中 `baselineSampleReliability = n / (n + 100)`。至少需要两个有效特征且有效权重和不低于 `0.35`，否则该场为 outcome-only。

本场隐藏表现证据为有效 z-score 的加权平均，并通过 `tanh` 压缩到 `[-1, 1]`：

```text
evidence = tanh(weightedMean(z) / 1.5)
```

这里的 evidence 是相对同类基线的本场表现观测，不是 MMR 分数。它与胜负结果共同用于单场更新，但不能独立决定最终方向。

### 9.4 MMR 影响

首轮候选使用：

```text
performanceDelta = evidence
                 * min(abs(baseDelta) * 0.25, modeHardCap)
                 * evidenceReliability
```

硬上限：

- 职责竞技、开放竞技：`4.0 MMR`
- 角斗竞技：`2.0 MMR`
- 职责快速、开放快速：`1.5 MMR`
- 角斗快速：首版 `0.0 MMR`

角斗快速只有 39 条表现记录，首版固定 outcome-only。只有累计达到至少 100 条、覆盖至少两个赛季、win/loss 均达到最低样本并通过独立影子验证后，才能在新模型版本中评估不超过 `0.5 MMR` 的修正。

所有模式继续遵守：胜局最终变化不得为负，败局最终变化不得为正，平局不得超过模式总上限，非有限输入产生 0 表现修正。

## 10. 验证设计

### 10.1 时间前向验证

按账号内部时间排序，建立 5 个 expanding-window folds。每折只用过去建立基线和状态，预测未来。禁止随机拆分导致同一时期、同一英雄分布泄漏。

### 10.2 账号留一

分别用一个匿名账号建立基线，在另一个账号上评估。由于只有两个账号，账号留一只作为强制诊断：明显恶化会拒绝模型，通过也不能证明跨用户泛化。

### 10.3 表现层主要指标

个人表现层不能只靠安全约束晋级，必须同时满足：

- 下一场 Brier 和 log loss 相对 P0 均不得恶化超过 `0.005`。
- 至少 3/5 个时间前向折不差于 P0。
- ECE 恶化不超过 `0.01`。
- 每个职责在竞争模式中正修正和负修正占比均至少 20%。
- 每个职责、环境、结果类别的平均表现修正绝对值不超过 `0.15 MMR`，防止系统性奖励胜方或惩罚败方。
- 竞技模式表现修正绝对值 P75 至少 `0.5 MMR`，否则判定为不可感知；P95 不得超过对应硬上限。
- 硬上限命中率不超过 5%。
- 任一特征的绝对贡献占比不超过 40%。
- 非有限输出、方向反转和缺失值奖励均为 0。
- 坦克、输出、支援的有效特征组合不得完全相同。

如果数据天然导致某个职责无法同时满足正负对称、下一场预测和职责差异，v4 不激活，不为该职责生成固定非零兜底。

### 10.4 黄金对局测试

使用纯合成数据建立至少以下排序：

- 同为胜局：优秀表现 > 普通表现 > 较差表现，但三者最终均加分。
- 同为败局：优秀表现 > 普通表现 > 较差表现，但三者最终均扣分。
- 相同原始统计在不同英雄或模式基线下可以得到不同 evidence。
- 高伤害高死亡不能必然优于中等伤害低死亡。
- 高治疗不能在异常资源占用且低生存时自动获得最高支援评分。
- 缺失职责核心统计不会得到奖励。

### 10.5 正式端到端对账

在隔离数据库中对同一批合成普通和角斗比赛分别运行训练投影、影子重放和正式重建，并断言 input hash、职责、模式、特征、evidence 和 delta 完全一致。必须额外验证：

- 角斗 `match_players` 为 0 行时正式重放仍产生角斗事件。
- 普通正式输入包含非空表现特征。
- “模式贡献”出现角斗竞技。
- 模式汇总分别累计 `baseDelta`、`performanceDelta` 和 `finalDelta`。

## 11. 早停和运行时间预算

所有数值程序必须使用 release 构建。投影结果在一次实验内缓存，候选之间不得重复读取 SQLite 或解析详情 JSON。

以下预算约束单轮数据审计、模型比较和影子重放，不把首次 Rust 编译、自动化测试或安装包构建伪装成“训练耗时”。工程实现和发布构建另行计时，但执行期间必须持续报告当前步骤；不得让用户在没有状态更新的情况下等待。

阶段预算：

| 阶段 | 预算 | 早停条件 |
| --- | ---: | --- |
| 数据完整性和覆盖审计 | 2 分钟 | 角斗正式投影为 0；关键职责无正负样本；特征覆盖不足 |
| 500 行烟测 | 1 分钟 | 非有限、方向反转、单边分布、训练/运行输入不一致 |
| 基础算法挑战赛 | 5 分钟 | B1/B2 均未优于 B0，立即固定 B0 |
| 表现模板比较 | 10 分钟 | P1/P2/P3 均未通过最低分布或下一场预测门槛 |
| 全量顺序影子重放 | 10 分钟 | 端到端计数、校准、幂等或隐私检查失败 |
| 单轮硬上限 | 30 分钟 | 终止进程并输出失败报告 |

screen 阶段没有晋级候选时立即结束。只有候选已经通过所有低成本门禁后，才允许执行最多 200 次 bootstrap 作为最终置信区间诊断；v4 首版禁止 1,000 和 10,000 次 bootstrap。

程序至少每 30 秒输出一次：阶段、已完成匿名单元数、总单元数、耗时和预计剩余时间。不得输出路径、账号、比赛、英雄原始标识或数据行。连续 60 秒没有进度更新视为执行异常并停止。

## 12. Artifact、持久化与版本

v4 artifact 必须包含：

- schema 和算法版本
- 选中的基础算法或保留 B0 的原因
- 每个职责和环境选中的表现模板
- 特征方向、固定产品权重和可靠度规则
- 分层基线的更新算法、最低样本、MAD floor 和可靠度规则
- 模式比例上限和总变化上限
- 下一场预测、分布和端到端验收摘要
- 配置哈希和确定性摘要

artifact 不得包含账号、BattleTag、玩家名、比赛 ID、文件路径、原始 JSON、SQLite 内容、token、cookie、authorization 或 credential。

v4 首版不把当前账号全量历史计算出的最终中位数或 MAD 固化进 artifact。每次重放都从空的匿名基线状态开始，按时间顺序重建；这样当前比赛不会使用未来比赛或自身统计作为基线。基线状态可以作为本次事务内缓存优化，但持久化缓存不得成为评分真源，删除缓存后完整重放必须得到相同结果。

数据库使用模型版本 `4`，继续复用事务激活框架。v4 写入完成后必须核对事件数、三个职责摘要、模式摘要、artifact 哈希和重放摘要，再把 v4 设为唯一 active。失败时完整回滚，v2 和 v3 保持不变。

每条 v4 事件至少持久化：

- `baseAlgorithm`
- `baseDelta`
- `performanceTemplate`
- `performanceEvidence`
- `evidenceReliability`
- `performanceDelta`
- `finalDelta`
- 匿名中文解释因子

如果需要新增列，必须提供幂等前向迁移以及 pre-MMR、v1、v2、v3 升级测试。

## 13. 查询和产品展示

生涯 MMR 页面继续说明“本地模型推算，并非暴雪官方隐藏分”。页面显示 active 模型版本和基础算法。

模式贡献必须分开显示：

- 胜负基础贡献
- 个人表现贡献
- 最终累计贡献

单场解释最多展示三个主要因素，例如“生存高于同类基线”“治疗接近同类基线”“死亡高于同类基线”。不得只显示笼统的“个人表现修正”，也不得暴露原始训练系数、身份或隐私字段。

如果当前 active 仍是 v2，页面不得暗示个人表现已经生效。如果 v4 未通过门禁，产品继续显示 v2，不显示未激活的影子结果。

## 14. 激活决策

v4 只有满足以下全部条件才允许激活：

1. 统一投影和正式重放端到端一致。
2. 三个职责均选择通过门禁的表现模板；不允许固定非零兜底。
3. 下一场预测指标不超过允许恶化范围。
4. 正负修正、可感知幅度、职责差异和特征贡献满足门禁。
5. 角斗竞技正式事件和模式贡献均非零。
6. 完整顺序重放无非有限、越界、方向反转或幂等差异。
7. artifact 隐私扫描和配置哈希验证通过。
8. 后端、前端、Tauri 构建、干净快照构建和安装版烟测通过。

任何一项失败都停止激活并保留 v2。报告必须明确写出失败阶段、耗时、失败门槛、已完成验证和建议，不再用“保证上线”措辞包装失败结果。

## 15. 实施顺序

1. 修复并统一普通/角斗训练与正式投影，不训练模型。
2. 新增匿名 v4 数据能力审计，验证按职责、模式、结果和特征的最低样本。
3. 引入 `skillratings`，实现 B0/B1/B2 顺序挑战赛。
4. 实现无泄漏分层基线和 P0/P1/P2/P3 固定模板。
5. 实现下一场预测、分布、账号留一和黄金对局门禁。
6. 在 30 分钟预算内执行首次受控实验；失败即报告并停止。
7. 只有实验通过后才实现 v4 artifact、数据库事件、事务激活和 UI。
8. 执行完整发布验证，不通过则保持 v2 active。

这一顺序确保最便宜、最关键的数据和模型假设先被验证。不得在模型尚未证明有效前投入 UI、迁移、安装包或高次数统计计算。

## 16. 算法来源与依赖边界

v4 的设计参考以下公开材料：

- Microsoft Research《TrueSkill 2: An improved Bayesian skill rating system》：参考“胜负与个人统计共同观测隐藏表现”、参赛时长、多模式相关和激励一致性原则。
- Rust `atomflunder/skillratings`：作为 Glicko-2 和 TrueSkill 基础层挑战者实现，采用仓库提供的 MIT/Apache-2.0 许可版本并固定依赖版本。
- Weng-Lin / OpenSkill：参考开放的多人贝叶斯评分设计，但因当前对手历史不完整，首轮不启用完整团队 Weng-Lin。
- Glicko-2 官方论文：参考 rating deviation、volatility 和时间不活跃处理。

引用论文不等于声称实现官方 TrueSkill 2。v4 不复制来源不明的非官方 TrueSkill 2 仓库代码；新增第三方依赖前必须核对许可证、维护状态、Rust 最低版本、serde 支持和确定性行为。最终报告必须列出实际采用的 crate、版本和许可证。
