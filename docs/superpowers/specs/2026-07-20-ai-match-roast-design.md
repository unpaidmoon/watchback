# AI 对局锐评功能设计

> 状态：已确认，等待实施。本文记录已经逐项确认的产品方向与实现边界。

## 1. 产品目标

用户在对局详情中手动点击“生成 AI 锐评”，应用将匿名化后的必要对局数据发送给 DeepSeek，生成一份简短、有依据、以取悦用户为目标的中文赛后锐评。

核心体验：

- 胜利时判断用户是带飞、躺赢还是团队取胜。
- 失败时判断用户是尽力、背锅还是集体崩盘。
- 可以调侃当前用户，但不做人身攻击。
- 可以指出一个匿名队友英雄作为“大爹”“短板”或“主锅”。
- 每个结论必须有本地数据支撑。
- AI 负责写段子，本地程序负责计算事实。
- 不生成长篇专业复盘。

## 2. 使用流程

```text
用户打开对局详情
  -> 点击“生成 AI 锐评”
  -> Rust 查询当前账号数据库
  -> 复用已有对局标签
  -> 计算具体事实和队友关系
  -> 构造最小化 AI 数据包
  -> 调用 DeepSeek
  -> 校验结构化输出
  -> 本地缓存
  -> 在详情页展示锐评
```

未点击按钮时，不发送任何数据。

## 3. 对局类型

复用已有 `match_evaluations.primary_tag`，不创建第二套 AI 对局类型。

| 已有标签 | AI 锐评方向 |
|---|---|
| 带飞局 | 集中夸用户，必要时指出被带飞的短板 |
| 躺赢局 | 调侃用户，找出队内大爹 |
| 尽力局 | 给用户找台阶，寻找失败主锅 |
| 背锅局 | 适度损用户，指出是谁在尽力带他 |
| 顺风局 | 夸团队整体，不强行找短板 |
| 惜败局 | 强调比赛接近、关键反差或高置信主锅 |
| 胜利局/失败局 | 数据不足时使用中性娱乐文案 |

现有标签负责确定用户在故事中的角色；新增素材选择器负责寻找队友关系和具体证据。

对局标签规则版本作为锐评元数据保存，用于解释结果来源，但不自动使已经成功生成的锐评失效。锐评一旦生成，作为该场对局的永久附属内容保留。

生成锐评时后端必须先确保该对局的现有标签就绪：

- 详情完整但 `match_evaluations` 缺失时，现场补算该场标签后继续。
- 补算成功后使用已有主标签和证据标签。
- 数据仍不足以形成四种核心标签时，使用现有“胜利局”或“失败局”中性回退类型。
- 标签缺失本身不阻止锐评，只降低关系候选的激进程度；证据不足时不指定大爹、短板或主锅。

## 4. 关系类型

每场最多选择一个匿名队友作为关系对象。

| 关系类型 | 含义 |
|---|---|
| `weak_link` | 用户带飞了谁 |
| `ally_carry` | 用户靠谁取胜，或谁在尽力带他 |
| `scapegoat` | 失败主锅 |
| `team_effort` | 团队共同发挥 |
| `team_collapse` | 全队共同崩盘 |
| `self_roast` | 当前用户自己背锅 |
| `none` | 没有足够证据 |

关系对象只显示英雄名称，例如“队友死神”“队友安娜”“我方莱因哈特”，不显示玩家名、BattleTag 或 ID。

只有至少两项相互支持的异常事实时，才允许指定“大爹”“短板”或“主锅”。证据不足时必须回退到团队或局势点评，不能强行点名。

### 4.1 职责差异

大爹、短板和主锅候选必须按职责使用不同证据，不能使用一套统一公式：

- 坦克：重点考虑存活、击杀参与、减伤、承伤、受到治疗和资源转化。承伤高本身不能作为负面证据。
- 输出：重点考虑击杀、最后一击、伤害、击杀参与、死亡和受到治疗后的产出。伤害高但击杀转化低可以作为反差事实，但不能单独定为主锅。
- 支援：重点考虑治疗、助攻、死亡、伤害和同职责对位。伤害低本身不能作为负面证据。
- 开放职责或职责缺失时，优先使用可靠的英雄职责映射；仍无法确定时只使用通用生存、参与和排名事实，不做职责专属判断。

关系候选仍需至少两项相互支持的事实，并保留反证。任何单项统计都不能独立决定“大爹”“短板”或“主锅”。

关系候选以相对指标为主：

- 队内排名和全场排名。
- 同职责对位差。
- 团队伤害、治疗、承伤和受到治疗占比。
- 击杀参与、生存和资源转化等组合指标。
- 当前对局内部的明显反差。

不使用“伤害低于一万”一类固定绝对阈值直接判定大爹、短板或主锅。固定数值只用于数据完整性、零值异常和极短对局等有效性检查。对局时长、模式和英雄差异必须通过相对指标或职责规则消化。

支援的“队伍资源不足”可以作为短板或主锅方向，但必须组合判断：

- 治疗量或团队治疗占比明显偏低。
- 相比队友支援或对方同职责明显落后。
- 队伍死亡、生存或实际受到治疗数据同时表现出资源不足。
- 支援自身伤害较高而治疗明显偏低时，可以形成“把支援玩成输出”的戏剧化反差。

“伤害高于治疗”只能作为辅助事实，不能单独定罪。不同支援英雄的正常输出与治疗结构不同；当其他证据不足时，只允许把它描述为打法倾向，不得断言其导致队伍失败。

首版不模拟完整英雄技能，也不要求覆盖所有英雄。采用“职责通用规则 + 少量明确例外”：

- 坦克、输出、支援各有一套通用规则，覆盖所有英雄。
- 只为通用规则容易误判的英雄添加静态画像，例如偏输出型支援、偏治疗型支援或混合型支援。
- 英雄画像使用既有英雄 GUID 作为稳定键，中文名只用于最终展示和 AI 数据包。
- 英雄画像只调整指标解释与候选阈值，不分析技能命中、大招时机、站位、克制过程或完整技能机制。
- 英雄画像缺失时使用保守的职责通用规则，不阻塞锐评，也不因单项数据定罪。
- 后续只在真实样本显示某英雄被频繁误判时增加例外，不预先维护完整英雄百科。

### 4.2 本地规则与 AI 职责

以下处理必须在 Rust 本地完成：

- 英雄职责和支援英雄打法画像。
- 数据完整性检查与样本有效性判断。
- 队内排名、全场排名、同职责对位和占比计算。
- 同职责赛季均值差。
- 连胜连败状态。
- 角斗回合转折。
- 大爹、短板和主锅候选选择。
- 支持事实、反证、关系类型和置信度。
- 最终允许发送给 AI 的最小化数据包。

AI 不读取完整原始计分板，也不自行选择主锅。提示词只负责：

- 根据已经确认的事实生成本场封号。
- 把戏剧化事实改写成简短中文段子。
- 根据本地指定的关系对象生成点评。
- 遵守不虚构、不做人身攻击和不越过反证边界等文案规则。

提示词必须明确声明：输入中的 `facts` 是可陈述事实，`counterFacts` 是表达边界；模型不得新增数值、玩家、事件或因果关系。

本地素材构造只处理当前一场约十至十二名玩家和固定数量指标，目标性能预算如下：

- SQLite 查询不超过 50ms。
- 本地排名、画像和规则判断不超过 10ms。
- JSON 构造与校验不超过 10ms。
- 本地阶段总耗时目标不超过 100ms；超过时视为实现或查询问题。

锐评主要等待时间应来自 DeepSeek 网络请求和生成，而不是本地判定。

## 5. 数据选择原则

发送给 AI 的不是完整对局详情，而是本地已经计算好的喜剧素材。

### 5.1 公共数据

- 胜负。
- 模式。
- 地图中文名。
- 比分。
- 时长。
- 当前用户英雄和职责。
- 不发送双方完整英雄阵容。
- 只发送当前用户英雄、选定的大爹/短板/主锅英雄，以及本地已经验证的阵容事实。
- 已有对局标签、评级、证据标签、置信度和规则版本。

### 5.2 当前用户数据

- 击杀、助攻、死亡。
- 伤害、治疗、减伤。
- 承伤、受到治疗。
- 最后一击、目标时间。
- 队内排名。
- 全场排名。
- 同职责对位差。
- 不使用当前英雄个人赛季均值作为比较数据，也不为锐评新增该聚合查询。
- 复用现有同职责赛季均值，比较击杀、死亡、伤害和治疗；不新增当前英雄均值。
- 资源占比及转化指标。
- 加入选中对局的连续状态：此前连胜/连败次数、当前是否延续或终结连续状态。
- 连续状态由 Rust 基于同账号、同赛季对局按时间顺序计算，不依赖前端列表分页或筛选。
- 平局和未知结果中断连续状态；只向 AI 发送次数和事件类型，不发送历史对局列表。

### 5.3 关系候选数据

根据对局标签选择一种关系候选：

- 队内大爹。
- 被带飞短板。
- 失败主锅。
- 全队共同表现。

每个候选包含：

- 英雄名称和职责。
- 两至四条支持事实。
- 一至两条反证。
- 候选置信度。

反证用于限制 AI 的推断边界。例如某位队友死亡很多但伤害不低，AI 可以吐槽其生存问题，但不能描述为“完全没有作用”。

```json
{
  "subject": "队友死神",
  "facts": [
    "死亡数全队最高",
    "贡献全队 28.9% 的死亡"
  ],
  "counterFacts": [
    "伤害队内第 3",
    "最后一击队内第 3",
    "并未大量占用团队治疗"
  ],
  "confidence": "high"
}
```

## 6. 具体事实

最终根据有效证据动态选择三至四条最值得进入正文的事实。证据不足时保留三条，不允许为固定数量补凑弱事实。素材选择器必须去重同类事实，避免用多个排名、占比或差值重复表达同一项表现。

事实优先级如下：

1. 全场第一或队内第一。
2. 同职责对位明显领先或落后。
3. 与现有同职责赛季均值差异明显。
4. 高资源占用与低产出的反差。
5. 高输出与低击杀转化的反差。
6. 高死亡与低参与率。
7. 低死亡与高参与率。
8. 比分、数据和胜负之间的反差。

当前用户、关系对象、比赛局面、同职责赛季均值和连续状态共同进入事实候选池。最终选择以对局标签相关性、证据强度、戏剧反差、可理解性和同类去重为准，不固定要求每种来源至少出现一条。某一类事实明显更强时，可以占据多条，但不得重复表达同一指标。

示例：

- 死亡数全队最低。
- 减伤队内第二。
- 治疗量高于同职责赛季均值 31%。
- 队友死神贡献全队 28.9% 的死亡。

事实由 Rust 计算并格式化，AI 不负责重新计算、排序或修改数值。

## 7. 戏剧化事实

本地额外选择两至三条适合写段子的局面反差：

- 用户表现突出但只差一分落败。
- 用户和主锅死亡数差距明显。
- 全队伤害领先但击杀、存活或比分落后。
- 某队友获得大量治疗但产出靠后。
- 某位队友多项数据统治全场。
- 用户自己多项落后却获胜。
- 同职责对位明显悬殊。
- 当前对局延续连胜或连败。
- 当前对局终结此前的连胜或连败。

AI 可以把事实改写成有戏剧性的中文，但不得改变数值，也不得把相关性描述成确定因果。

## 8. 角斗模式

角斗除公共数据外，增加回合级素材：

- 首版只针对整场角斗生成一份锐评，不在用户切换单个回合时分别调用 AI。
- 所有回合用于本地计算整场走势、关键回合和转折点。
- 一场角斗只产生一份缓存和一次首次生成费用。

- 每回合胜负和比分。
- 当前用户的回合资金和最终资金。
- 当前用户最终资金的队内排名。
- 用户各回合表现变化。
- 已映射的装备和异能中文名称。
- 落后后翻盘。
- 决胜回合突然崩盘。
- 更换构筑后表现改善或下降。

回合转折必须由本地数据明确证明，不能让 AI 根据最终总经济反推某个回合发生了什么。

首版不比较双方团队资金总和，也不生成“经济领先却输掉”或“经济落后却赢下”等因果事实。`worth` 与 `endWorth` 只作为当前用户资金及队内排名使用：

- 最终资金排名只使用 `endWorth`，不混用或回退到 `worth`。
- 只有同队所有可比较玩家的 `endWorth` 都存在时，才生成“最终资金队内第 N”事实；任何一人缺失就放弃该事实。
- “全队经济最高”统一表达为“当前用户最终资金队内最高”，不代表本方整体经济领先对方。
- 资金排名可以用于娱乐描述，不能被解释为构筑价值、战斗力或胜负原因。

回合胜负序列可以生成明确的走势事实，例如：

- 连输三回合后连赢四回合，描述为“让三追四”。
- 连赢后被追平并输掉决胜回合。
- 决胜回合完成反超。
- 某一方连续赢得若干回合。

```json
{
  "turningPoints": [
    "前三回合全部失败，随后连赢四回合，完成让三追四",
    "当前用户最终资金队内第 1"
  ]
}
```

未映射的原始 GUID 不发送。

## 10. AI 输出

取消“本场封号”标签，直接把封号文本作为主标题并增大字号。标题不超过十六个汉字。

三至四条本地事实继续作为生成依据，但前端不把它们机械罗列成事实清单。AI 必须把事实、局面反差和关系点评组织成两至三句语义连贯的中文正文，总长度不超过一百八十个汉字。

```json
{
  "award": "里阿尔托机甲售后主管",
  "commentary": "你在前排维持战线，死神在出生点维持刷新率。比分只差一分，但双方的生存理念差了十六次死亡；他的伤害不是没打，主要是活着的时间不太够用。",
  "usedFactIds": ["self-lowest-deaths", "scapegoat-death-share", "close-score"]
}
```

其中：

- `award` 由 AI 生成。
- `commentary` 由 AI 生成，必须是连贯正文，不得退化为数据条目拼接。
- `usedFactIds` 不向用户展示，只用于 Rust 校验正文引用的素材全部来自本地允许事实。
- 关系对象和关系类型由本地决定，AI 负责把对应点评自然融入正文。

## 11. 文案规则

- 首版固定一种“有梗、偏锐利、但不做人身攻击”的文风，不提供温和、毒舌或教练等风格选择。
- 风格不进入用户设置，也不产生额外缓存分支。
- 目标是让用户觉得好笑、被理解。
- 可以损当前用户的本局表现。
- 可以吐槽匿名队友英雄在本局的数据表现。
- 不评价玩家人格、智力或现实身份。
- 不使用玩家名、地域、性别等信息。
- 不虚构站位、技能命中、语音交流或具体操作过程。
- 不把相关性描述成确定因果。
- 胜利时优先营造庆祝感。
- 失败时至少给用户一个真实台阶。
- 用户自己是背锅局时，也要以自嘲和找补结尾。
- 背锅局必须明确展示当前用户有数据依据的问题，不为了取悦用户强行把锅转给其他队友。
- 背锅局文案采用“指出问题 -> 娱乐化自嘲 -> 真实找补”的顺序；找补必须来自实际亮点或中性事实，不能伪造优点。
- 避免持续羞辱同一个英雄对象。
- 避免直接复刻网络现成段子。

```json
  "stream": false,
  "temperature": 0.9,
  "max_tokens": 500
}
```

使用 Flash 非思考模式，以降低延迟和成本。Rust 必须执行：

- 首版固定使用 `deepseek-v4-flash`，指挥台和对局详情不提供模型选择。
- 模型名称属于应用内部版本化配置，未来通过应用版本升级调整。
- 首版不使用流式输出。Rust 接收完整响应并完成全部校验后，前端一次性展示并永久保存结果。
- 不向前端发送未经校验的部分文本，避免校验失败时已经显示的内容被撤回。

- JSON 解析。
- 必填字段校验。
- 字段长度限制。
- 数组数量限制。
- 封号不超过十六个汉字，正文为两至三句且不超过一百八十个汉字。
- 关系对象一致性校验。
- `usedFactIds` 必须是输入事实编号的子集，并达到最低事实覆盖要求。
- 禁止模型新增玩家或事实。
- 空内容时有限重试一次。
- `finish_reason=length` 时视为失败。
- 单次生成设置六十秒客户端超时；超时后取消本地等待并显示“锐评生成超时，请重试”。

模型名属于运行配置，最终实现时应能够升级，不把即将弃用的旧模型名固化到数据库 schema。

## 13. API Key

采用用户自带 DeepSeek API Key：

- API Key 配置放在指挥台页面，即 `/onboarding` 的 `OnboardingPage`。
- 指挥台增加独立的“AI 锐评”设置区，不在对局详情内嵌 Key 输入框。
- 设置区属于应用级配置，不依附当前游戏账号或赛季。
- 对局详情未配置 Key 时，点击生成只在锐评区域显示“请先在指挥台配置 DeepSeek API Key”。
- 未配置状态不自动跳转指挥台、不发起 DeepSeek 请求，也不保留待生成任务。
- 由 Rust 保存到 Windows Credential Manager。
- React 永远无法读取完整 Key。
- 指挥台只显示“已配置并验证”或“未配置”，不显示 Key 末尾字符或任何凭据片段。
- Rust 返回前端的状态 DTO 不包含完整 Key、掩码 Key 或可用于推断 Key 的字段。
- Key 不进入 SQLite、`user_settings.json`、日志或安装包。
- 不提供删除 Key 操作；用户可以提交并验证新 Key 后覆盖现有 Key。
- 不复用网易大神凭据存储文件。

保存行为：

- 用户保存 Key 时由 Rust 先调用 DeepSeek 的认证模型列表等不生成文本的轻量接口测试连接。
- 只有认证和连接验证成功后，才写入 Windows Credential Manager。
- 验证失败时显示中文原因，不保存无效 Key。
- 替换现有 Key 时先验证新 Key；新 Key 验证失败必须保留旧 Key。
- 测试连接不调用对话补全，不生成锐评，也不写入对局缓存。

## 14. 隐私边界

绝不发送：

- 玩家名、BattleTag、`bnetId`。
- 对局 ID 和账号 ID。
- `rawJson`。
- 收藏备注。
- 本地路径和数据库内容。
- 网易大神 token、cookie、customerToken。
- 错误 payload。
- 未映射的玩家、英雄或地图隐私 ID。
- 完整历史对局列表。

首版不显示首次生成确认弹窗，也不保存确认状态。用户手动点击“生成 AI 锐评”后直接调用。指挥台的 DeepSeek API Key 设置区使用常驻说明交代基本数据边界，不在对局详情中重复打断用户：

> 生成锐评时会向 DeepSeek 发送匿名化后的本局统计，不发送玩家名称、账号标识或登录凭据。

## 15. 缓存

每场对局只保存一份成功锐评，以当前账号数据库和 `match_id` 建立唯一关系。对局标签规则版本、AI 素材版本、提示词版本和模型作为元数据保存，不参与自动失效：

```text
账号数据库 + 对局
```

保存：

- 通过校验的锐评结果。
- 模型名。
- 生成时间。
- 版本信息。

不保存：

- API Key。
- 完整请求。
- DeepSeek 原始响应。
- 思维内容。
- 玩家身份数据。
- Token 用量和估算费用。

产品界面不显示 Token 用量或估算费用，本地数据库和诊断信息也不保存该用量字段。

锐评像收藏备注一样跟随每场对局永久保存。实现复用收藏功能的生命周期、查询装配、数据库迁移模式和 UI 位置，但使用独立的 AI 锐评表和 DTO，不把结果写入收藏备注字段。

已有成功锐评时直接显示，不重复调用。首版不提供“换一个”或重新生成入口：

- 同一缓存版本下，每场对局只成功生成一次。
- 生成失败不写入成功缓存，用户可以重试。
- 生成成功后始终读取缓存，不再次消耗 API 额度。
- 不保存历史版本，也不提供文案变体切换。
- 对局标签规则、素材规则、提示词或模型升级时，旧锐评继续展示，不自动失效或重写。
- 删除 DeepSeek API Key 不删除已经保存的锐评。
- 对局或账号被正常删除时，锐评随其数据库生命周期删除，不留下孤立记录。

## 16. UI 初稿

在普通和角斗对局详情中复用同一个 AI 锐评组件。

组件位置与收藏备注保持一致：

- 普通对局：AI 锐评显示在收藏对局/备注组件正上方。
- 普通独立详情和列表右侧嵌入详情使用同一组件和同一位置规则。
- 角斗对局：只在“角斗汇总”中显示 AI 锐评，并位于汇总收藏组件正上方。
- 角斗单回合不显示生成入口或锐评结果，切换回合不触发 AI 状态变化。
- 对局列表卡片不显示“已有 AI 锐评”标记，不新增 AI 锐评筛选，也不为此扩展列表 DTO。
- 尚未生成时只显示紧凑操作栏和“生成 AI 锐评”按钮，不预留完整报告高度。
- 生成成功后原位展开封号主标题和连贯正文，永久结果不再显示生成按钮。
- 成功结果不显示“AI 生成”标识、模型名、生成时间或其他技术元数据。

生成交互文案：

- 初始按钮：“生成 AI 锐评”。
- 请求期间轮播多条本地固定文案，不额外调用 AI。
- 请求期间禁用按钮和重复提交，不创建并发生成请求。
- 只有当前对局详情完整且能够构造有效素材时，才显示可点击的生成按钮。
- 详情缺失或后台处理中时显示“对局详情完整后可生成锐评”，不发起请求。
- 因详情不完整而禁用时不创建失败记录或永久锐评。
- 用户在生成过程中切换到其他对局时，不取消已经发出的请求。
- 应用级同时只允许一个锐评生成请求；后端使用独立的 AI 生成互斥状态，不占用赛季同步互斥锁。
- 当前请求未结束时，其他对局显示“另一场锐评正在生成”，不能启动第二次调用。
- 生成成功、失败或超时后必须释放互斥状态，使其他对局可以继续生成。
- 完成结果必须绑定发起时的账号和 `match_id`，写入原对局的永久锐评记录，不能写入当前后来选中的对局。
- 用户在生成期间切换游戏账号时也不取消请求。后端必须使用发起时捕获的账号上下文和数据库目标，结果只写入原账号、原对局。
- 新账号页面不得接收或显示原账号生成事件；返回原账号后从该账号数据库读取结果。
- 当前页面仍显示原对局时可以即时刷新；用户已经切走时不强行导航或打断，返回原对局后从数据库读取结果。
- 应用进程退出导致请求中止时不写入不完整结果，用户下次可以重新生成。

加载文案固定为以下六条，每约两秒按顺序切换并循环：

1. “正在翻阅本场数据…”
2. “正在寻找关键证据…”
3. “正在确认谁在带飞…”
4. “正在核对锅位归属…”
5. “正在申请本场封号…”
6. “正在组织锐评措辞…”

轮播只改变视觉文案；无障碍状态使用稳定的“正在生成 AI 锐评”，避免屏幕阅读器反复播报。禁用非必要位移动画，并遵守 `prefers-reduced-motion`。

组件状态：

- 未配置 API Key。
- 尚未生成。
- 正在生成。
- 生成成功。
- API Key 错误。
- 余额不足。
- 请求过多。
- 服务繁忙。
- 输出格式异常。

未配置状态使用稳定的行内中文提示，不使用弹窗或自动导航。

生成失败统一在锐评区域显示简短中文原因，并按错误类型提供恢复动作：

- API Key 无效：提示“DeepSeek API Key 无效，请在指挥台重新配置”，不提供原地重试。
- 余额不足：提示前往 DeepSeek 检查余额，不自动重试。
- 网络错误、请求过多或服务繁忙：保留当前对局状态并提供“重试”按钮。
- 输出为空、JSON 不合法或校验失败：后端可以在同一次用户操作中自动重试一次；仍失败时显示格式异常并提供“重试”按钮。
- 所有失败都不写入成功锐评表，不影响原对局详情、收藏或备注。

成功内容：

```text
放大显示的封号主标题，不显示“本场封号”标签
融合三至四条具体事实的两至三句连贯锐评正文
大爹 / 短板 / 主锅和角斗回合转折自然融入正文（如适用）
```

视觉遵循根目录 `design.md`。参考用户提供图片的信息层级和分段表达，但不复制其深色橙色品牌样式、署名、具体文案或视觉资源。

## 17. 首版范围

首版包含：

- API Key 设置。
- 手动生成。
- 所有详情完整的普通、竞技、快速、开放职责和角斗对局。
- 平局或无法形成强标签的对局使用中性锐评，不强行指定大爹、短板或主锅。
- 复用已有对局标签。
- 三至四条事实。
- 最多一个关系对象。
- 戏剧化事实。
- 封号主标题。
- 本地缓存。
- 完整错误状态。

首版不包含：

- 图片分享卡片。
- 一键复制。
- 自动生成。
- 多轮追问。
- 自定义提示词。
- 云端统一 API Key。
- 完整专业复盘。
- 多个主锅排行榜。
