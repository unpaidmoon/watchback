# OWStatsLocal 列表优先的赛季快速更新设计

日期：2026-07-17

## 1. 背景

现有 `QuickUpdate` 已经限制列表分页，并且只为新对局或扫描范围内缺失详情的对局请求详情。但它仍把详情抓取、数据库导入、完整赛季快照重建和控制台全量刷新放在同一个前台命令中。

以本机 S22 数据规模为例，SQLite 中约有 941 场对局和 941 份有效详情，原始详情 JSON 约 24～25 MB。即使没有新增对局，当前路径仍会重新读取、解析、脱敏并写出完整赛季快照。因此“更新”虽然不是全量重新下载，用户等待时间仍可能接近全量操作。

本设计把快速更新改为“列表优先、后台完善”：点击“更新”后，前台只检查五个标准模式的第一页并增量提交对局列表；详情、后续分页和完整快照在持久化后台任务中完成。用户在列表事务提交后即可继续查询对局。

## 2. 目标

- 最优先更新对局列表，而不是等待详情或快照。
- 五个标准模式第一页返回后，以短事务增量写入新对局，并立即向前端返回。
- 无新增时只更新轻量检查状态，不导入对局、不重建快照、不清理比赛缓存、不重新加载完整控制台。
- 新增对局的详情、玩家索引、投影、后续第 2～5 页和完整快照全部在后台完成。
- 后台运行期间，对局列表、详情页和其他只读查询保持可用。
- 后台任务可恢复、幂等、账号隔离，并且不会泄露凭据、玩家隐私标识或原始上游响应。
- 保留“全量抓取”的完整列表扫描和全详情刷新能力。

## 3. 非目标

- 不保证上游网络异常、429 或超时时仍能在固定墙钟时间内完成第一页请求。
- 不保证快速更新发现第 5 页以后的历史延迟数据；全量抓取仍是完整校验入口。
- 不在前台命令内等待详情覆盖率达到 100%。
- 不直接增量修改完整 JSON 快照；快照继续从 SQLite 一致状态重建。
- 不恢复旧 BattleTag 搜索或跨账号同步流程。
- 不允许同一账号、同一赛季同时运行多个快速更新或全量抓取任务。

## 4. 产品语义

### 4.1 前台完成的定义

“更新”按钮完成表示：

1. 五个标准模式的第一页已经完成检查，或已得到明确的部分失败结果。
2. 第一页发现的新对局已经提交到 SQLite。
3. 模式游标、最后检查时间和后台任务已经原子持久化。
4. 用户可以立即查询更新后的对局列表。

它不表示详情、后续分页或完整快照已经完成。

### 4.2 后台完成的定义

后台完成表示：

1. 需要继续的模式已经顺序扫描到可靠边界或第 5 页上限。
2. 本轮发现的新对局详情已经成功写入，或留下可重试的脱敏失败记录。
3. 玩家索引和派生投影已经随有效详情更新。
4. 完整赛季快照已经按最新数据库版本原子替换。

### 4.3 用户可见文案

- 无新增：`S22 已检查最新一页，没有发现新对局。`
- 第一页有新增：`S22 已新增 N 场对局，详情正在后台处理中。`
- 部分模式失败：`S22 已保存成功获取的数据；部分模式检查失败，正在后台重试。`
- 后台继续发现：`S22 又发现 N 场对局，正在补充详情。`
- 后台完成：`S22 更新完成，详情与本地快照已就绪。`
- 后台失败：`S22 对局列表已更新，后台处理失败，可重试。`

只有所有模式命中可靠边界时才可以表达“没有发现新对局”；异常响应或部分失败不得宣称已是最新。

## 5. 总体架构

快速更新拆成前台提交器和持久化后台工作器：

```text
前台命令
账号与目标校验
  -> 读取同步游标
  -> 五个模式并发请求第一页
  -> 短事务写入列表、游标和后台任务
  -> 返回前端并释放查询

后台工作器
继续扫描第 2～5 页
  -> 分批提交新列表
  -> 抓取新增详情
  -> 更新详情、玩家索引和投影
  -> 按数据库版本重建并原子替换快照
```

SQLite 是运行时唯一事实来源。完整赛季 JSON 是可重建的兼容产物，不得阻塞前台列表可见性。

## 6. 前台快速阶段

### 6.1 请求预算

前台只执行：

- 五个标准模式各一次第一页列表请求。
- 零次个人卡片请求。
- 零次赛季统计请求。
- 零次对局详情请求。
- 零次完整快照重建。

五个标准模式为：

- `normal:sport`
- `normal:leisure`
- `fight:QuickFight`
- `fight:LeisureFight`
- `fight:SportFight`

模式间并发，单模式前台阶段永远不请求第二页。现有限速、429 重试、脱敏和账号级并发限制继续生效。

### 6.2 请求形式

每个模式的游标记录已验证的请求形式：

- `implicitCurrentSeason`：当前赛季省略 `season` 参数。
- `explicitSeason`：显式携带目标赛季。

历史赛季迁移默认使用 `explicitSeason`，当前赛季迁移默认使用 `implicitCurrentSeason`。前台只使用一种形式，不执行回退探测。需要备用形式验证时，将验证任务放入后台，不阻塞前台返回。

### 6.3 第一页判定

第一页可能产生以下结果：

- `unchangedBoundary`：页面有效，所有有效对局均已存在且不晚于水位。
- `emptyBoundary`：页面结构有效且为空。
- `newEntries`：存在本地没有的对局或晚于水位的对局。
- `unsafe`：业务码异常、结构异常、缺少有效 `matchId` 或时间，不能推进水位。
- `failed`：网络、认证、限速重试耗尽或其他请求错误。

对于没有历史对局水位的模式：

- 有效空页可以记录为 `emptyConfirmed`。
- 有效非空页中的对局作为最新列表写入，并安排后台继续分页。
- 不再因为缺少水位而在前台扫描五页，也不丢弃有效第一页条目。

### 6.4 前台事务

所有成功模式的第一页结果在一个短事务中提交：

1. 幂等插入或更新第一页对局条目。
2. 只对可靠页面推进对应模式游标。
3. 更新赛季 `last_checked_at`。
4. 为需要继续分页、抓取详情或验证备用请求形式的工作创建持久化任务。
5. 如果新增列表数据，递增 `season_revision`。

异常或失败模式不推进游标。其他成功模式的数据仍然提交，不因单模式失败整体回滚。

### 6.5 前端返回

事务提交后命令立即返回 `QuickListCommitSummary`，至少包含：

- `season`
- `newListMatches`
- `dataChanged`
- `partialFailure`
- `pendingDetails`
- `backgroundStatus`
- `checkedAt`
- 五个模式的第一页结果和脱敏错误类型

前端根据返回值：

- 只失效当前账号、当前赛季的对局列表缓存。
- `dataChanged = false` 时不清理比赛页缓存，不调用完整 `loadDashboard()`。
- `dataChanged = true` 时立即重新查询当前赛季列表和轻量赛季状态。
- 结束“更新中…”的前台阻塞状态并恢复页面查询；同赛季的“更新”和“全量抓取”仍由后台状态禁用。

## 7. 持久化同步状态

所有状态位于账号自己的 SQLite，不跨账号共享。

### 7.1 `season_sync_state`

每赛季一行：

- `season`
- `season_revision`
- `snapshot_revision`
- `last_checked_at`
- `background_status`
- `pending_detail_count`
- `updated_at`

### 7.2 `season_sync_cursors`

每赛季、每标准模式一行：

- `season`
- `match_kind`
- `game_mode`
- `request_shape`
- `latest_begin_ts`
- `empty_confirmed`
- `last_checked_at`
- `last_full_fetch_at`
- `last_stop_reason`

唯一键为 `(season, match_kind, game_mode)`。

### 7.3 后台任务表

`season_sync_jobs` 保存任务主状态：

- 内部任务 UUID
- 赛季和目标数据版本
- 阶段、状态、重试次数和下次重试时间
- 创建、开始、完成和更新时间
- 脱敏错误分类

`season_sync_job_modes` 保存各模式的下一页、页数预算、请求形式和停止原因。

`season_sync_job_matches` 保存本轮已经写入、仍需抓取详情的 `match_id` 和任务状态。`match_id` 已经是数据库主键，但不得进入用户可见日志或错误文案。

任务表不得保存凭据、Token、Cookie、Authorization、完整请求 URL、原始上游响应或玩家显示身份。

### 7.4 迁移

迁移必须前向兼容、幂等并覆盖升级库测试：

- 从现有 `matches` 派生已有标准模式的最新有效水位。
- 缺少对局的模式保持 `empty_confirmed = false`，等待一次有效空页或全量抓取确认。
- S22 等历史赛季使用显式 season 请求形式；当前赛季使用省略 season 的默认形式。
- 不修改、删除或重新解释现有对局、详情、玩家索引和同步错误。

## 8. 后台工作器

新增账号级 `BackgroundSeasonSyncManager` 作为 Tauri 应用状态，负责：

- 从 SQLite 领取持久化任务。
- 保证同一账号、同一赛季最多一个活动任务链。
- 在程序启动时把遗留 `running` 任务恢复为 `queued`。
- 向前端发送带账号和赛季作用域的进度事件。
- 与账号切换、重新登录和删除生命周期协调。

后台任务不依赖当前页面选择，也不持有前端组件状态。

### 8.1 后续分页

- 只有第一页结果为 `newEntries`、`unsafe` 或需要备用请求形式验证时才安排后续工作。
- 单模式内部从第 2 页顺序推进。
- 包含前台第一页在内，每模式总预算仍为 5 页。
- 每页发现的新列表立即通过短事务写入，并递增 `season_revision`。
- 每次提交后发送账号和赛季作用域的 `season-list-updated` 事件。
- 命中已知水位、有效空页或页数上限后停止。

### 8.2 详情补全

- 只请求本轮实际扫描到、数据库尚无有效详情的对局。
- 详情并发继续遵守现有上游限制，默认最多两个并发。
- 有效详情按小批次提交，并同步更新玩家索引和派生投影。
- 详情失败不删除列表行，也不覆盖已有有效详情或玩家索引。
- 每批提交后更新 `pending_detail_count` 和后台状态事件。

### 8.3 快照重建

- 无数据变化时不创建快照任务。
- 本轮分页和详情任务稳定后，只合并执行一次快照重建。
- 重建开始时记录目标 `season_revision`。
- 在一致的 SQLite 读事务中读取完整赛季数据。
- 临时文件写完后再次读取当前版本；版本不一致时丢弃临时结果并重新排队。
- 版本一致时原子替换正式快照，并更新 `snapshot_revision`。
- 快照失败时保留上一份有效文件，不影响 SQLite 查询。

## 9. 查询与并发

- SQLite 保持 WAL、忙等待和短写事务策略。
- 前台列表事务和后台批次事务不得包围网络请求。
- 对局列表、详情、复盘、排行和好友查询不获取后台同步互斥锁。
- 同一账号、同一赛季后台运行时，其“更新”和“全量抓取”禁用。
- 其他赛季的只读查询保持可用。
- 账号切换后，旧账号任务可以继续使用固定的账号目录；事件必须携带内部账号作用域，前端忽略非当前账号事件。
- 删除账号前必须取消或等待该账号后台任务停止，不能在持有数据库或快照文件句柄时删除目录。
- 全量抓取开始前必须确认同赛季没有活动后台任务。全量抓取成功后，它可以将较旧的快速任务标记为 `superseded`。

## 10. 失败与恢复

### 10.1 第一页部分失败

- 保存所有成功模式的数据。
- 失败模式不推进游标，并创建后台重试任务。
- 返回 `partialFailure = true`。
- 不显示“没有发现新对局”或“已是最新”。

认证失效、账号目标不匹配等全局错误仍在任何写入前失败关闭。

### 10.2 后续分页失败

- 已提交的列表不回滚。
- 保存失败页和剩余页数预算。
- 按受控退避重试；重试耗尽后显示可重试状态。

### 10.3 详情失败

- 对局列表继续可见。
- 保留已有有效详情、玩家索引和投影。
- 将失败项保持为可重试状态，错误内容递归脱敏。

### 10.4 快照失败

- 保留旧快照和新的 SQLite 数据。
- 单独重试快照任务，不重新抓取列表或详情。
- 明确显示“对局数据已更新，本地快照重建失败”。

### 10.5 重启恢复

- 启动时把没有活动工作器对应的 `running` 任务恢复为 `queued`。
- 对局、详情和任务表唯一键保证重复执行幂等。
- 恢复时从数据库事实重新判断已经完成的详情和版本，不盲信旧内存状态。

## 11. UI 与事件

前台阶段显示：

```text
正在检查五个模式的最新对局
正在写入最新对局列表
```

前台提交后结束按钮的阻塞状态。赛季行独立显示后台状态：

- `正在继续检查后续页面`
- `详情处理中：N 场`
- `正在重建本地快照`
- `后台处理失败，可重试`

新对局没有详情时：

- 列表仍显示来自列表接口的时间、模式、结果、地图和英雄等已有字段。
- 详情入口显示“详情处理中”。
- 收到详情完成事件后定向刷新该场详情。

后台事件至少包括：

- `season-list-updated`
- `season-detail-updated`
- `season-background-progress`
- `season-background-completed`

所有事件携带内部账号作用域、赛季、阶段和匿名计数。不得携带原始对局 ID、玩家 ID、凭据或上游响应。

列表更新事件按账号和赛季防抖，避免后台连续提交造成刷新风暴。

## 12. 性能合同

### 12.1 无变化

- 五个模式各请求第一页一次。
- 元数据请求为 0。
- 详情请求为 0。
- 对局导入为 0。
- 快照重建为 0。
- 比赛缓存清理为 0。
- 控制台全量刷新为 0。
- 只提交游标和 `last_checked_at`。

### 12.2 有变化

- 前台仍只等待五个第一页和列表短事务。
- 最后一个第一页响应返回后，约 1000 场的 S22 夹具上，本地提交目标不超过 250ms。
- 前台命令返回后 500ms 内发起当前赛季列表刷新。
- 后续分页、详情和快照耗时不计入前台按钮等待时间。

这些是本地处理和请求预算合同。上游延迟、429 和网络失败必须被测量并诚实展示，但不能伪造固定墙钟保证。

## 13. 诊断

前台摘要和后台状态分别记录匿名耗时：

- `page1DurationMs`
- `foregroundCommitDurationMs`
- `foregroundTotalDurationMs`
- `backgroundListDurationMs`
- `backgroundDetailDurationMs`
- `snapshotDurationMs`
- 每模式请求页数和停止原因

诊断不得包含 URL 查询参数、Token、Cookie、Authorization、原始响应、对局 ID 或玩家 ID。

UI 在开发诊断区域或安全日志中显示阶段耗时，使性能问题可以定位为上游列表、详情、数据库还是快照，而不是只显示一个总时间。

## 14. 测试与验收

### 14.1 前台请求账本

录制服务器必须证明：

- 五个标准模式各收到一次第一页请求。
- 前台返回前没有个人卡片、赛季统计、详情和第二页请求。
- 后台测试屏障暂停时，前台命令仍然返回。

### 14.2 立即可查

- 第一页新对局提交后立即查询 SQLite，列表可见。
- 后台详情暂停时，旧列表查询和新列表查询均成功。
- 前端只失效目标账号和赛季的列表缓存。

### 14.3 无变化快速返回

- 不调用对局导入器。
- 快照内容、文件修改时间和 `snapshot_revision` 不变。
- 比赛页缓存不清理，完整控制台不重新加载。
- 只更新游标检查时间。

### 14.4 后台流水线

- 第二至第五页只在前台返回后开始。
- 后续页新对局分批写入并发送列表事件。
- 详情成功后更新详情、玩家索引和投影。
- 本轮只合并重建一次快照。
- 数据版本变化时旧快照结果不能覆盖新版本。

### 14.5 失败恢复

- 第一页部分失败仍保存成功模式数据。
- 分页失败从失败页恢复。
- 详情失败保留列表和旧有效详情。
- 快照失败保留旧快照。
- 重启后恢复 `running` 任务且不重复对局、详情或索引。

### 14.6 账号与隐私

- 账号切换期间后台任务仍写入原账号数据库。
- 非当前账号事件不刷新当前页面。
- 账号删除与后台文件句柄安全协调。
- 任务表、事件、错误和快照继续通过敏感字段扫描。

### 14.7 全量抓取回归

- 全量抓取继续扫描到空页。
- 全量抓取继续请求所有去重后的赛季详情。
- 全量抓取成功后生成完整、脱敏、原子替换的快照。
- 失败刷新不删除旧有效详情或玩家索引。

## 15. 实施边界

预期主要变更范围：

- `src-tauri/src/season_fetch.rs`：第一页前台检查与后台分页拆分。
- `src-tauri/src/sync/facade.rs`：前台列表提交门面。
- `src-tauri/src/sync/persist.rs`：列表先行的短事务。
- `src-tauri/src/sync/snapshot.rs`：版本化快照重建。
- `src-tauri/src/db.rs` 或现有迁移模块：同步状态和任务表迁移。
- 新的后台同步管理模块：任务领取、恢复和事件发送。
- `src-tauri/src/commands.rs`：前台命令与后台管理器接线。
- `src/shared/types.ts`、`src/shared/api.ts`：前台摘要与后台状态协议。
- `OnboardingPage.tsx`、赛季工作台和比赛列表缓存：定向刷新与后台状态。
- 同步、数据库迁移、缓存、账号隔离和隐私测试。

不得借此重构无关的登录、排行、复盘、角斗映射或资源打包模块。

## 16. 采用方案

采用“第一页列表前台提交，后续分页、详情和快照后台完成”的架构。

不采用直接增量修改快照，因为排序、去重、替换和恢复复杂度会显著提高 SQLite 与快照不一致风险。

不采用快速更新永久不维护快照，因为现有兼容流程仍需要最终获得完整快照。
