# 战报角斗好友协作与动态赛季设计

## 状态

- 日期：2026-07-16
- 状态：用户已确认
- 范围：战报页和其复用的好友协作模块

## 背景

战报页“队友协作”中的好友亲密度、高频组合和模型榜单目前只读取普通模式的 `match_players` 投影，因此角斗竞技 `SportFight` 与角斗快速 `LeisureFight` 不参与计算。战报页同时把赛季选项固定为 S21、S22、S23，导致已经同步到本地的 S15、S20 等赛季无法选择。

本设计同时解决这两个问题：在不改变既有 UI、评分门槛和普通模式投影语义的前提下，将可靠识别出的角斗好友数据加入三个协作模块，并让战报页按本地实际同步数据动态发现赛季。

## 目标

1. 好友亲密度同时统计普通模式、角斗竞技和角斗快速。
2. 高频组合同时统计三类对局，并使用角斗最后有效回合中的英雄。
3. 模型榜单使用角斗最后有效回合的玩家统计，不使用 `totalCount` 代替。
4. 战报页展示本地数据库实际存在的所有赛季，不再固定为 S21、S22、S23。
5. 所有战报标签和好友协作请求严格使用同一个选中赛季。
6. 历史数据库无需重新同步即可读取已有角斗详情。

## 非目标

- 不改变指挥台的赛季同步入口。
- 不新增全局赛季状态或“一键同步全部”。
- 不改变好友详情页的近期对局、地图拆分等独立展示合同。
- 不把角斗玩家写入普通模式专用的 `match_players`。
- 不根据重复出现的队友推断好友关系。
- 不调整现有榜单名称、排序规则、样本门槛、亲密度权重或前端布局。
- 不把最后回合统计换算成每分钟或每 10 分钟指标。

## 方案选择

### 采用：查询时解析角斗详情

普通模式继续读取 `match_players`。角斗模式在好友分析请求期间查询 `matches` 与 `match_details`，从 `raw_detail_json` 中解析最后有效回合，并转换为现有聚合器可以消费的内部行模型。

选择该方案的原因：

- 已有历史库中的角斗详情可以立即参与计算。
- 无需修改 SQLite schema、导入器或执行历史回填。
- 保持 `match_players` 的普通模式语义，避免影响筛选、复盘和其他聚合。
- 当前单赛季角斗详情规模适合请求时解析。

### 不采用：扩展 `arena_match_players`

为 `arena_match_players` 增加好友标记、英雄和统计字段虽然能减少查询时解析，但需要前向迁移、幂等回填、升级库测试和导入器改造，超出本次最小改动范围。

### 不采用：扩大 `match_players`

将角斗写入 `match_players` 会破坏其既有普通模式边界，并可能让未审计的查询自动纳入角斗数据，回归风险不可控。

## 后端架构

### 角斗解析边界

在 `analytics` 内增加独立角斗解析单元，职责仅包括：

1. 查询当前筛选范围内 `SportFight` 与 `LeisureFight` 的 `matches` 和 `match_details`。
2. 解析 `raw_detail_json.payload.data.roundCountList`。
3. 从尾到头选择最后一个结构有效、且 `teammateList` 包含当前玩家的回合。
4. 从当前玩家行读取 `friendBnetIds`，只把其中同时出现在队友列表的玩家识别为好友。
5. 将每局当前玩家及好友转换为亲密度、组合和模型聚合所需的内部行。

角斗解析单元不返回原始 JSON，不向 DTO 暴露玩家 ID 之外的新字段，也不负责 UI 文案或榜单排序。

### 当前玩家与好友识别

- 当前玩家身份沿用本地已同步账号的内部身份解析，不从重复次数猜测。
- 好友身份唯一来源是该局当前玩家行的 `friendBnetIds`。
- 敌方玩家永不进入好友协作。
- 同一局、同一好友最多生成一条统计行；重复原始项按 `bnetId` 去重。
- 无法可靠定位当前玩家、缺少 `friendBnetIds` 或没有已识别好友时，该角斗局不进入三个协作模块。

### 最后有效回合

“最后有效回合”定义为 `roundCountList` 中按原顺序最后一个满足以下条件的对象：

- 回合是 JSON 对象；
- `teammateList` 是非空数组；
- 队友列表中能定位当前玩家。

该回合决定：

- 当前玩家与好友的英雄；
- 模型榜单使用的击杀、助攻、死亡、英雄伤害、治疗、减伤、承伤和受疗等字段；
- 高频组合的成员英雄。

不得使用 `totalCount` 补模型统计，也不得在找不到最后有效回合时伪造统计。英雄在同一角斗对局的各回合不会变化，因此最后有效回合同时满足高频组合的英雄身份需求。

角斗整局胜负、开始时间、赛季和模式继续使用规范化后的 `matches` 行。模型统计直接使用最后有效回合的原始数值，不做时长归一化。

### 合并与聚合

`get_friend_analytics` 先取得普通好友行和角斗好友行，再合并后调用现有聚合逻辑：

- 好友亲密度沿用组排人数权重：双排每场 5，三排 3，四排 2，五排或六排 1。
- 角斗的组排人数等于当前玩家加该局可靠识别出的好友数量，不把普通队友计为组排成员。
- 高频组合沿用当前玩家加已识别好友的稳定成员 key、三场门槛、胜率和排序规则。
- 模型榜单沿用五场好友门槛、分位带、评分公式、每榜人数和排序规则。
- 普通与角斗遇到同一好友时按内部 `bnetId` 合并累计。
- 好友代表英雄从合并后的普通与角斗样本中按既有规则选择。

普通模式结果在没有角斗好友数据时必须与改动前完全一致。

### 筛选行为

角斗行遵循现有 `FriendAnalyticsFilters`：

- `season`、`result`、日期范围和 `mode` 在数据库查询阶段过滤；
- `hero` 使用最后有效回合中的好友英雄过滤；
- `map` 使用规范化后的对局地图身份过滤；
- 未提供筛选时，战报只传当前选中赛季，不跨赛季聚合。

## 战报动态赛季

### 数据合同

`PersonalSeasonReview` 新增 `availableSeasons` / `available_seasons`。后端从 `matches` 查询实际存在的不同赛季，并按降序返回。赛季发现包含普通与角斗数据，确保主要包含角斗数据的已同步赛季也能进入战报。

一次战报请求返回：

- 后端最终选中的 `summary.season`；
- 动态 `availableSeasons`；
- 该赛季的既有战报内容。

### 赛季选择规则

- 未指定赛季时选择 `availableSeasons` 中最新的赛季。
- URL 中任意正整数赛季都可以提交给后端，不再限制为 S21、S22、S23。
- 请求的赛季不在本地列表时，后端回退到最新可用赛季。
- 后端回退或默认选择后，前端同步 `selectedSeason` 和 URL。
- 没有本地赛季时返回空列表，并沿用现有空状态。
- 赛季列表只属于战报页，不新增全局赛季 store。

### 前端行为

删除 `PersonalReviewPage` 中固定的 `selectableSeasons`。`PageSeasonSelect` 使用当前战报响应的 `availableSeasons`，保持降序显示。赛季切换继续同时刷新个人战报与 `getSeasonAnalysis`，因此概览、成就、好友亲密度、高频组合和模型榜单共享同一个赛季。

独立好友分析页继续维持自己的页面级赛季状态；由于它复用相同后端好友分析，所以角斗好友数据也会生效，但本次不重构其赛季选择 UI。

## 错误处理与隐私

- 单局角斗 JSON 无法解析或字段不足时跳过该局，不让整个战报请求失败。
- 不在日志、错误消息或测试输出中打印原始详情、原始玩家 ID、`friendBnetIds`、凭据或 token-like 字段。
- 英雄或玩家展示名缺失时使用既有中文稳定兜底，不向发布 UI 暴露原始 GUID 或隐私 ID。
- 新逻辑只读取已脱敏持久化详情，不新增 raw JSON 持久化位置。
- `availableSeasons` 只包含整数赛季编号，不包含账号或玩家信息。

## 测试设计

### 后端好友协作

使用完全合成、脱敏的普通和角斗数据建立以下回归：

1. 同一好友在普通、`SportFight`、`LeisureFight` 中出现，三类对局共同累计亲密度。
2. 两类角斗数据都能进入高频组合，并与普通样本共同达到三场门槛。
3. `totalCount`、较早回合和最后有效回合故意提供不同统计，断言模型榜单只使用最后有效回合。
4. 角斗最后回合模型统计与普通模式统计合并后共同达到五场门槛。
5. 缺少当前玩家、缺少 `friendBnetIds`、没有有效回合或只有敌方匹配 ID 时不进入好友协作。
6. 同一好友在一个回合重复出现时每局只计一次。
7. S15、S20、S23 同库时只聚合请求的单一赛季。
8. 没有角斗数据时，现有普通模式亲密度、组合和模型榜单结果不变。

### 后端动态赛季

1. 插入 S15、S20、S23 数据，断言 `availableSeasons` 为 `[23, 20, 15]`。
2. 未指定赛季时选择 S23。
3. 请求 S15 时返回 S15。
4. 请求不存在的正整数赛季时回退到 S23。
5. 只有角斗数据的赛季仍出现在 `availableSeasons`。
6. 空数据库返回空列表和既有空战报结构。

### 前端合同

1. 战报源代码不再包含固定 `selectableSeasons`。
2. 赛季选择器读取 `review.availableSeasons`。
3. `parseSeasonParam` 接受 S15、S20 和其他正整数，拒绝零、负数和非数字。
4. 后端选择赛季与 URL 不一致时，页面使用后端结果修正 URL。
5. 切换动态赛季后，个人战报和好友协作请求使用同一赛季。

## 验收标准

1. S15、S20 等本地已有赛季自动出现在战报赛季选择器。
2. 选中任一赛季后，所有战报标签和好友协作模块只显示该赛季数据。
3. 好友亲密度和高频组合累计角斗竞技与角斗快速。
4. 模型榜单的角斗指标可由差异化 fixture 证明来自最后有效回合，而不是 `totalCount` 或较早回合。
5. 无可靠好友身份的角斗队友不会被误报为好友。
6. 现有普通模式行为、阈值、排序、中文 UI 和隐私边界保持不变。
