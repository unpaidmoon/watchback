# OWStatsLocal 个人稳定版与可持续开发设计

## 文档状态

- 日期：2026-07-10
- 状态：已批准
- 适用仓库：`D:\Codex\OW_data\owstats-local`
- 当前产品：`apps/owstats-desktop`
- 目标：在保留现有代码和本地数据的前提下，将项目收敛为可重复开发、可验证、可回退的个人稳定版。

## 1. 背景与判断

项目已经具备可用的 Tauri 2 + React + TypeScript + Rust + SQLite 桌面产品骨架，普通/角斗对局、战报、排行、好友分析、多赛季状态和本地同步均有实际实现。Rust 集成测试也覆盖了导入、查询、评分、同步与多赛季隔离。因此，本轮不推倒重写，也不另建第二套内核。

当前主要问题不是缺少功能，而是工程边界和交付纪律不足：

- 工作区长期混合多个主题，难以独立审查和回退。
- `src/shared/assets.ts` 与 Vite 配置依赖开发机绝对路径和被忽略的本机参考文件。
- 同步代码仍使用 `CARGO_MANIFEST_DIR` 推导运行数据位置。
- 已确认的“当前登录账号本人同步”方向与现有 BattleTag 绑定实现不一致。
- 部分持久化 payload 和 SQLite raw 数据仍可能保留 token-like 字段。
- 数据库迁移、历史回填、同步互斥和错误记录幂等性未形成统一机制。
- `styles.css`、`queries.rs`、`review.rs`、`analytics.rs`、`sync.rs` 等文件职责过重。
- 前端测试大量依赖源码字符串断言，项目没有统一验证入口和 CI 门禁。

解决方式是暂停新增功能，先执行分层稳定化。

## 2. 已确认目标与约束

### 2.1 目标

稳定化完成后，项目应满足：

- 当前已有成果全部可恢复，不因整理工作区而丢失。
- 现有 SQLite 和赛季数据通过备份及前向迁移保留，不使用删库重建作为修复手段。
- 在当前目录和另一个目录的干净 checkout 中均可测试、构建并启动 Tauri 开发模式。
- 构建和运行不依赖 `D:\Codex\...`、`/@fs/` 或被 `.gitignore` 忽略的本机输入。
- 日志、错误、诊断 JSON、赛季 JSON、SQLite raw 字段和 UI DTO 不泄露 token-like 字段。
- 数据库升级、重复同步和中断恢复有自动化回归测试。
- 后续 AI 开发使用统一任务模板、验证门禁和小提交纪律。

### 2.2 本轮非目标

- 不新增产品功能或重做现有页面视觉。
- 不构建第二套应用内核。
- 不制作或验收 MSI、NSIS 安装包。
- 不处理代码签名、自动更新和安装/卸载流程。
- 不接入 Windows Credential Manager。
- 不引入新的状态管理框架、数据库 ORM 或 DTO 自动生成系统。

## 3. 安全基线与 Git 工作方式

### 3.1 两分支模型

```text
bundled 当前提交
├─ codex/stabilization-snapshot
│  └─ 保存当前全部有效改动的原始快照提交
└─ codex/stabilization
   └─ 从原始基线重新按主题拆分、审查和提交
```

`codex/stabilization-snapshot` 只承担恢复职责，不继续开发，也不改写历史。`codex/stabilization` 是正式治理分支。

### 3.2 快照规则

建立快照前：

1. 记录当前分支、基准提交、`git status --short` 和未跟踪文件清单。
2. 扫描凭据、真实数据、浏览器 profile、构建产物和 token-like 字段。
3. 快照只包含有效源码、测试、文档和产品资产。
4. 在仓库外生成脱敏补丁备份，并保存基准提交哈希与文件清单。
5. 实际执行一次恢复验证。

### 3.3 正式提交规则

- 一次提交只解决一个问题或完成一个纯重构边界。
- 行为修复、测试补强、纯文件拆分和文档修改尽量分开提交。
- 每个提交必须可独立验证和回退。
- 不提交 `test-results`、`dist`、`target`、本地数据库、凭据、浏览器 profile 或真实数据 dump。
- 新功能冻结期间，只允许发布阻断修复、隐私修复、数据迁移、必要重构和测试补强。

## 4. 目标架构边界

### 4.1 前端

```text
src/
├─ app/                 路由、应用壳、全局初始化
├─ features/
│  ├─ command-center/   登录、同步、赛季健康
│  ├─ matches/          筛选、列表、普通/角斗详情
│  ├─ review/           个人战报与成就
│  ├─ ranking/          英雄/地图排行
│  └─ friends/          好友分析
└─ shared/
   ├─ api/              Tauri invoke 封装
   ├─ contracts/        TypeScript DTO
   ├─ assets/           资源解析
   └─ ui/               通用组件与设计变量
```

### 4.2 Rust

```text
src-tauri/src/
├─ app/commands         参数校验、路径获取、错误转换
├─ infrastructure/
│  ├─ paths             app_data 与开发资源路径
│  ├─ database          连接、迁移、事务
│  └─ credentials       本地凭据读写与状态
├─ sync/
│  ├─ identity          当前登录账号识别
│  ├─ client            请求、限速、重试
│  ├─ fetch             赛季数据抓取
│  └─ persist           脱敏、落盘、导入
└─ domain/
   ├─ matches
   ├─ arena
   ├─ review
   ├─ ranking
   └─ friends
```

### 4.3 拆分原则

- 先解决资源、路径、隐私和迁移阻断项，再拆业务大文件。
- 每次只拆一个职责，并保持现有 Tauri command、DTO 和页面行为稳定。
- 纯重构提交不得混入产品行为变化。
- 暂时手动维护 Rust/TypeScript DTO，通过序列化契约测试防止漂移。
- CSS 按设计变量、应用壳和功能模块拆分，不同时重做样式。
- 文件超过约 600 行或同时承担三种以上职责时必须评估拆分，但不按行数机械切割。

## 5. 开发版可移植性

### 5.1 资源构建

- 前端不再直接导入 `docs/reference` 下被忽略的本机文件。
- 从本机参考数据中提取产品实际需要的最小、脱敏配置，并作为正式构建输入提交。
- 由固定脚本根据 manifest 从已跟踪的 `assets/` 准备 Vite 资源。
- 所有路径使用仓库相对路径，构建后使用稳定的 `/assets/...` URL。
- 资源准备脚本必须校验 manifest 指向的文件，存在缺失时立即失败。
- 不要求本轮执行 `tauri build`，但 `npm run build` 产物不得包含开发机绝对路径。

### 5.2 运行数据路径

新增统一 `AppPaths` 或等价路径服务，至少定义：

```text
app_data/
├─ owstats.sqlite3
├─ settings.json
├─ player-profile.json
├─ credentials.json
├─ current-player.json
├─ seasons/
└─ diagnostics/
```

- Tauri command 只能通过该服务获取运行数据路径。
- `CARGO_MANIFEST_DIR` 仅允许测试、构建脚本和显式开发工具使用。
- 写文件使用原子替换，避免同步中断留下半文件。
- 另一个目录中的干净 checkout 必须能够执行测试、构建和 `npm run tauri:dev`。

## 6. 同步身份与隐私

### 6.1 身份模型

同步产品方向以 `2026-07-03-phase-8-login-account-season-sync-design.md` 为准：桌面端只同步当前浏览器登录账号本人数据。

- BattleTag 输入、`searchBnetAccount` 和旧目标绑定不再作为产品主流程。
- 认证凭据与玩家数据目标分为不同的内部类型。
- UI 只能看到账号识别状态、显示名和识别时间，不能看到数据目标 secret。
- 旧 `.dashen_player_target.json` 通过一次迁移转为新语义；迁移完成后不再作为同步前置条件。

### 6.2 Secret 存储边界

本轮不接入 Windows Credential Manager。secret 暂时保存在 Tauri app data，但必须满足：

- secret 结构与公开状态 DTO 分离。
- `Debug`、错误转换和序列化状态不得输出 secret。
- 文件使用原子写入。
- 注销删除认证 secret、目标 secret 和识别状态，但保留历史战绩数据库。
- 测试使用构造值，不读取真实凭据。

### 6.3 单一脱敏入口

建立一个共享的递归脱敏/删除函数，覆盖大小写和常见别名。以下输出必须经过该入口：

- 赛季 JSON 和诊断 JSON。
- SQLite raw entry/detail/profile 字段。
- `sync_errors` 和用户可见错误消息。
- 日志、测试快照和返回给前端的 raw JSON。

上游原始 payload 只允许短暂存在于内存。Git 忽略不构成隐私边界。

### 6.4 存量迁移

1. 扫描现有赛季 JSON 和 SQLite raw 字段，不打印命中的原值。
2. 创建时间戳备份。
3. 对副本执行脱敏迁移。
4. 验证数据行数、赛季数、对局数和详情数不变。
5. 原子替换原文件。
6. 迁移失败时保留原始数据并明确报告。

## 7. 数据库迁移与运行稳定性

建立显式迁移注册表，例如：

```text
v1 基础比赛数据
v2 match_players.role_type
v3 arena_match_players 与索引
v4 raw JSON 脱敏、索引和错误记录治理
```

每个迁移必须：

- 在单个事务中执行。
- 更新 schema version。
- 重复初始化不产生副作用。
- 使用旧数据库 fixture 验证升级。
- 迁移前创建 SQLite 备份。
- 失败时回滚并保留原数据库。

同时完成：

- 角斗玩家投影按赛季检查和回填，不使用“全表非空即完成”的判断。
- `sync_errors` 使用去重键或保留策略，避免重复同步无限追加。
- SQLite 配置合理的 busy timeout，并明确读写连接策略。
- 桌面同步命令增加进程内互斥；UI 禁用按钮不能作为唯一并发保护。
- 重复同步和中断恢复测试验证 matches、details、投影和错误记录均保持可控。

## 8. 测试与统一门禁

### 8.1 单一验证入口

新增仓库级脚本：

```powershell
.\scripts\verify.ps1
```

执行顺序：

1. 敏感字段与绝对路径扫描。
2. 资源 manifest 完整性检查。
3. 前端类型检查、单元测试和构建。
4. Rust 格式、Clippy 和集成测试。
5. 旧数据库升级测试。
6. `git diff --check`。

CI 只调用同一个脚本，避免本地与 CI 规则漂移。

### 8.2 测试分层

- Rust 集成测试继续覆盖同步、导入、迁移、查询和多赛季隔离。
- 上游协议测试使用本地 recording server，不读取真实凭据。
- TypeScript 单元测试覆盖筛选、缓存、格式化和派生逻辑。
- 为指挥台、赛季切换和对局筛选增加少量真实组件测试。
- 现有源码字符串测试暂时保留；触及对应功能时逐步替换，不一次性重写。
- 数据库迁移必须使用旧版 SQLite fixture，不允许只测空库。
- `cargo clippy` 先以报告模式运行；清理已有告警后再转为阻断门禁。

## 9. 轻量项目管理

只新增一份进度表：`docs/stabilization-progress.md`。

```text
编号      问题                    优先级  状态
STAB-001  安全快照                P0      待开始
STAB-002  拆分当前未提交成果      P0      待开始
STAB-003  资源与路径              P0      待开始
STAB-004  同步身份与隐私          P0      待开始
STAB-005  数据库迁移与恢复        P0      待开始
STAB-006  模块化与质量门禁        P1      待开始
```

状态只允许：`待开始`、`进行中`、`已验证`、`阻塞`。任何时刻只允许一个任务处于 `进行中`。

每个 AI 任务必须给出：

- 任务编号和目标。
- 允许修改与禁止修改的路径。
- 验收命令。
- 是否涉及数据库、隐私、资源或上游协议。
- 完成后的差异、测试和剩余风险报告。

## 10. 完成定义

任务只有同时满足以下条件才可标记为 `已验证`：

- 行为与设计一致。
- 回归测试通过。
- 没有新增绝对路径或敏感数据输出。
- 没有夹带无关文件。
- 文档和进度表已更新。
- 对应提交可独立回退。

稳定化项目完成时还必须满足：

- 当前工作区成果已拆分为可审查提交，正式分支工作树干净。
- 当前目录和异目录干净 checkout 都通过统一验证脚本。
- 旧 SQLite 副本升级成功，历史对局与详情计数不变。
- 持久化输出敏感字段扫描为零。
- 重复同步、中断恢复和多赛季隔离测试通过。
- 核心大文件完成按职责拆分，或在进度表中给出有依据的延后决定。

## 11. 分阶段实施顺序

### 阶段 0：冻结与安全快照

建立快照分支、快照提交和仓库外脱敏补丁，验证恢复路径。

### 阶段 1：拆分当前未提交成果

按以下主题重建正式提交：

1. 协作规则与阶段文档。
2. 多赛季页面兼容。
3. 角斗玩家索引与历史回填。
4. S23 地图预览映射与资产。
5. 对应测试修正。

### 阶段 2：可复现开发环境

移除绝对路径和本机隐藏输入，建立资源准备、资源校验和统一运行数据路径。

### 阶段 3：同步与隐私收口

落实当前登录账号本人同步、单一脱敏入口、存量数据备份与迁移。

### 阶段 4：数据库与运行稳定性

建立迁移注册表、逐赛季回填、错误记录治理、busy timeout 和同步互斥。

### 阶段 5：渐进式模块化

按职责逐步拆分 `styles.css`、`queries.rs`、`review.rs`、`analytics.rs`、`sync.rs`、`MatchesPage.tsx` 和 `OnboardingPage.tsx`。

### 阶段 6：质量门禁与稳定标签

完成统一验证脚本、关键组件测试、简单 Windows CI 和异目录干净 checkout 验收，最后创建个人开发稳定版标签。

## 12. 后续文档关系

- 本文定义稳定化的产品、架构和流程边界。
- `docs/stabilization-progress.md` 只记录执行状态和证据。
- 后续实施计划应把每个阶段拆成小任务，并给出精确文件、测试和提交边界。
- 安装版发布应在个人开发稳定版完成后另立设计，不得混入本轮计划。
